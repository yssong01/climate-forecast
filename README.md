# 환경 예보 (climate-forecast)

기상청 ASOS 지상관측 데이터로 **+6시간 뒤 기온·강수·극한기상 확률**을 산출하는 3축 멀티모달 파이프라인입니다.

논문 **Tri-CHEF**(*Complex-Hermitian Embedding Fusion for Korean Multimodal Retrieval*, Zenodo 프리프린트, DOI [10.5281/zenodo.20034370](https://doi.org/10.5281/zenodo.20034370))의 **3축 융합 수식만** 빌려와, 원 논문의 도메인(한국어 멀티모달 **검색**)과 전혀 다른 기후 예측에 이식한 실험입니다. 그 과정에서 발견한 문제들을 수식·코드·ablation으로 추적한 기록이기도 합니다.

> ⚠️ 이 저장소의 산출물은 **모델 출력값**이며 기상청의 공식 예보·특보가 아닙니다.
> 기상산업진흥법상 예보업은 등록 대상이므로, 실제 방재 판단의 근거로 사용해서는 안 됩니다.

### 출력값 추이

선과 막대는 최근 72시간의 **실측값**이고, ★ 표시가 이번 +6시간 산출값입니다.
예측 대상은 기온·강수 두 가지이며, 습도·기압은 상황 판단을 돕기 위한 참고용 실측값입니다.

![출력값 추이 탭](docs/images/tab-trend.png)

### 극한 기상

폭염·한파·황사 발생 확률과 판정 임계값(빨간 점선)을 함께 표시합니다.
각 확률이 어떤 정답 라벨로 학습되었는지, 그 라벨의 한계는 무엇인지도 화면에 명시합니다.

![극한 기상 탭](docs/images/tab-extreme.png)

### 성능 검증

회귀 MAE를 **기준선(학습을 전혀 하지 않는 자명한 방법) 대비 증감과 함께** 표시합니다.
MAE는 그 자체로는 좋고 나쁨을 말해주지 않고, 기준선보다 나은지로 판단해야 의미가 생깁니다.

- 기온 1.26°C — 퍼시스턴스(T(t+6)≈T(t)) 대비 **+61.7% 정확**
- 강수 0.170mm — '상시 0mm' 대비 **0.9% 미달**. 넘지 못한 지표도 그대로 노출합니다

극한기상은 정확도 대신 정밀도·재현율·F1로 평가합니다. 폭염이 전체의 1%뿐이라면
'항상 폭염 아님'이라고만 답해도 정확도가 99%가 되기 때문입니다.

![성능 검증 탭](docs/images/tab-performance.png)

## API 사용 시 주의사항

이 저장소를 직접 실행하려면 기상청 API허브(apihub.kma.go.kr) 인증키가 필요합니다.
**아래 제약을 먼저 확인하시기 바랍니다.**

### 1. 호출량 — 산출값 1건당 15회

| 구성 | 호출 수 |
|---|---|
| 대상 관측소 현재 관측 | 1 |
| 인접 11개 관측소 (Re축 공간 보간장) | 11 |
| 대상 관측소의 1·3·6시간 전 관측 (Im축 경향 벡터) | 3 |
| **합계** | **15** |

이 비용은 **접속자 수 × 화면 갱신 횟수**로 곱해집니다. 대시보드 기본 갱신 주기가
5분이므로, 캐시가 없으면 1개 관측소만 열어두어도 하루 4,320회에 도달합니다.

### 2. 차단 이력 — 누적 약 9,800건

대량 수집을 시도했을 때 **누적 약 9,800건 시점에서 차단**되었습니다
(2026-08-07 측정, 동시성 16 조건). 병렬화로 우회되지 않는 요청 수 기준의
제한으로 판단됩니다. 따라서 **과거 데이터 백필을 API로 시도하지 마십시오** —
기상자료개방포털의 파일셋(CSV 일괄 다운로드)을 사용해야 합니다.

### 3. 이 저장소의 대응

| 장치 | 내용 |
|---|---|
| **관측 시각 단위 캐시** | 산출 결과를 `(관측소, 관측 시각)` 키로 캐시합니다. ASOS는 매시 정각 1회 관측이므로 같은 정시 내 재조회는 동일한 값을 반환합니다. 따라서 호출량이 갱신 주기·접속자 수와 무관해지고 **관측소당 시간당 15회**로 고정됩니다 |
| **일간 상한** | `KMA_DAILY_CALL_BUDGET`(기본 3,000). 초과 시 예외를 발생시키지 않고 폴백으로 전환하며, 화면 상단에 그 상태를 표시합니다 |
| **사용량 표시** | 사이드바에 당일 누적 호출 수를 실측으로 노출합니다 |
| **폴백 데이터 격리** | `SUCCESS_LIVE` 응답만 모델 입력에 사용합니다. 폴백 레코드를 사용하면 합성 기본값이 실측으로 간주되어 보간장에 반영되기 때문입니다 |

검증 결과: 동일 정시에 2회 실행 시 호출 증가 **0건**.
실사용 기준 합산 예산은 대시보드 360~720회에 자동 갱신 288회를 더해
**약 650~1,000회/일**이며, 차단 지점의 7~10% 수준입니다.

인증키는 용도별로 분리해 두며, 저장소에는 포함되지 않습니다.

## 결과 요약

**학습 데이터**: 2023-01-01 ~ 2026-08-10, 12개 관측소(서울·인천·수원·춘천·강릉·대전·청주·전주·광주·대구·부산·제주) 통합, ASOS 시간자료 **332,195건** → (t, t+6h) 유효 쌍 **331,595개** → 학습 80% / 검증 20%.

### Tri-CHEF 3축 적용 효과 (2026-08-11 재학습, 동일 데이터·동일 분할)

| 구성 | 기온 MAE | 강수 MAE | 폭염 F1 | 한파 F1 | 황사 F1 |
|---|---|---|---|---|---|
| **Z축 단독** (Re·Im 입력 차단) | 1.4713 °C | 0.2051 mm | 0.752 | 0.389 | 0.206 |
| **3축 Tri-CHEF** (현행) | **1.2554 °C** | **0.1697 mm** | **0.842** | **0.667** | **0.588** |
| 개선폭 | **−14.7%** | **−17.3%** | +0.090 | **+0.278** | **+0.382** |

**공정성 조건**: 같은 데이터 캐시(API 재수집 없음) · 같은 SEED(42, 동일 분할) · 같은 조기 종료 기준(patience 20).
Z축 단독은 아키텍처·용량을 그대로 두고 **Re·Im 입력만 영벡터로 차단**해 정보 기여도만 분리했다(인코더는 동결).
두 체크포인트의 정규화 통계(`mean`/`std`)가 완전히 일치함을 코드로 확인했다.
게이트가 Z축에 99.72%를 배분하고 축 간 코사인이 전부 0.0000인 것이 차단이 실제로 작동했다는 증거다.

**가장 큰 효과는 극한기상 분류에서 나왔다.** 회귀(기온·강수)는 15% 안팎 개선이지만,
황사 F1은 0.206 → 0.588로 **2.9배**, 한파 F1은 0.389 → 0.667로 **1.7배**가 됐다.
드문 사건일수록 "지금 이 지점"만으로는 판단이 어렵고 주변·흐름 정보가 결정적이라는 뜻이다.

| 기온 MAE | **1.2554 °C** | 퍼시스턴스 T(t+6)≈T(t) : 3.2805 °C | **−61.7%** (개선) |

## 데이터 출처

**기상청 기상자료개방포털** (https://data.kma.go.kr/) — '파일셋' 메뉴에서 CSV 일괄 다운로드(시간자료, 2023~2026).

| 포털 내 경로 | 사용처 |
|---|---|
| 데이터 → 기상관측 → 지상 → **종관기상관측(ASOS)** | Z·Re·Im 3축의 원천 관측값 (332,195건) |
| 데이터 → 기상관측 → 지상 → **황사관측(PM10)** | 황사 헤드 정답 라벨 (PM10 1시간 평균 150㎍/㎥ 기준) |
| **날씨 이슈별 데이터** → 폭염 / 한파 / 황사 / 태풍 | 폭염·한파 헤드 정답 라벨 (실제 발표된 특보 기록) |

**API가 아니라 웹 포털 CSV로 백필한 이유**: apihub API로 대량 수집을 시도했을 때 **누적 약 9,800건 지점에서 차단**됐습니다(2026-08-07 실측, 동시성 16). 병렬화로 우회되지 않는 요청수 기준 상한이라, 과거 데이터 백필은 포털 CSV로 전환하고 API는 실시간 추론에만 씁니다(`import_kma_fileset.py`).

> 원본 CSV는 **EUC-KR** 인코딩입니다. UTF-8로 읽거나 grep하면 조용히 실패합니다.

## 아키텍처

```
                        ┌──────────────┐
  이웃 11개 관측소  ──▶ │ Re 인코더    │──┐
  IDW 공간보간장         │ (소형 CNN)   │  │
  (4ch, 32×32)          └──────────────┘  │    ModalityGate
                        ┌──────────────┐  │   (입력 조건부        s_i = √( (w_Re·Re_i)²
  1·3·6h 전 대비    ──▶ │ Im 인코더    │──┼──▶ softmax 배분) ──▶        + (w_Im·Im_i)²
  변화량 (12d)           │ (프로젝션)   │  │    Σw = 1                   + (w_Z ·Z_i )² )
                        └──────────────┘  │                                  │
                        ┌──────────────┐  │                                  ▼
  ASOS 수치 (12d)   ──▶ │ Z 인코더     │──┘                  ┌────────────────────────────┐
                        │ (MLP)        │                     │ 회귀 2 : 기온(Δ) · 강수     │
                        └──────────────┘                     │ 분류 3 : 폭염·한파·황사     │
                                                             └────────────────────────────┘
```

세 축은 각각 **다른 질문**에 답하고, 그 답을 하나로 합칩니다.

| 축 | 던지는 질문 | 입력 | 왜 Z축에서 유도 불가능한가 |
|---|---|---|---|
| **Z** (지금 여기) | 이 지점은 지금 어떤 상태인가? | 기온·강수·습도·풍속·풍향(sin/cos)·기압·강수형태·시각(sin/cos)·위도·경도 = 12차원 | — (기준축) |
| **Re** (주변) | 주변 지역은 지금 어떤가? | 대상 관측소를 **제외한** 11개 관측소의 같은 시각 실측을 IDW(역거리가중, power=2)로 ±3°(≈300km) 격자 32×32에 보간, 4채널(기온·습도·기압·풍속) | 다른 지점의 관측값은 이 지점 스냅샷에 존재하지 않음 |
| **Im** (흐름) | 어느 쪽으로 움직이는 중인가? | 같은 관측소의 1·3·6시간 전 대비 변화량 × 4변수 = 12차원 | ∂s/∂t 는 단일 시점 s(t) 하나만으로 계산 불가 |

- **융합**: 논문 Eq.1의 Hermitian-style modulus를 **원소별**로 적용 → 길이 64 벡터 `s`
- **축 가중치**: 고정 상수가 아니라 `ModalityGate`(12→16→3, softmax)가 **매 출력마다 재계산**. Σw=1로 고정해 스케일 자유도를 제거한다
- **회귀 헤드**: 기온은 퍼시스턴스 잔차(Δ) 방식, 강수는 Hurdle 구조 `σ(z₁) × softplus(z₂)`
- **분류 헤드**: 폭염·한파·황사 3종, 각각 독립 BCE. 대설은 한파∧호우의 논리곱이라 중복계산이 되므로 두지 않았다

### API 트래픽 — 5분 갱신이 왜 부하가 아닌가

**출력값 1건 = API 15회.** 대상 관측소 1 + 이웃 11곳(Re축 공간보간장) + 대상
관측소의 과거 1·3·6시간(Im축 경향벡터) = 15회.

문제는 이 비용이 **접속자 수 × 갱신 횟수**로 곱해진다는 점이다. 이 키는 누적
약 9,800건에서 차단된 이력이 있어(2026-08-07 실측) 그대로 두면 이틀이면
막힌다. 대시보드 기본 갱신 주기가 5분이므로:

| 조건 | 시간당 호출 | 일일 호출 |
|---|---|---|
| 캐시 없음, 5분 갱신, 1개 관측소 | 12회 × 15 = **180** | **4,320** |
| 캐시 없음, 5분 갱신, 접속자 3명 | 540 | 12,960 (**차단 지점 초과**) |
| **캐시 적용** (관측소·관측시각 단위) | **15** | **360** |

핵심은 **ASOS가 매시 정각 관측 1회, 약 10분 후 공개**라는 물리적 사실이다.
같은 정시 안에서 몇 번을 다시 조회해도 서버는 같은 값을 돌려준다. 그래서
`app.py`가 예측 결과를 `(관측소, 관측시각)` 키로 캐시하면:

```python
@st.cache_data(ttl=3600, show_spinner="관측 조회 중... (12개 관측소)")
def cached_predict(stn: str, obs_hour: str, _model, _ckpt) -> dict:
    return predict(stn=stn, model=_model, ckpt=_ckpt)
```

- 호출량이 **갱신 주기·접속자 수와 무관해지고 시계에만 묶인다**
- 관측소당 시간당 15회가 절대 상한 → 12개 관측소를 매시간 전부 조회해도 최악 4,320회/일
- 실사용(1~2개 관측소)에서는 **360~720회/일**, 차단 지점의 **3.7~7.3%**

실측 검증: AppTest로 같은 정시에 두 번 실행 → `1회차 15건 → 2회차 누적 15건
(증가 0건)`.

여기에 2차 안전장치로 프로세스 단위 일일 상한(`KMA_DAILY_CALL_BUDGET`, 기본
3,000)을 둔다. 상한 초과 시 예외 대신 폴백으로 내려가고, 사용량은 사이드바에
실측으로 표시된다. 상한 5건으로 강제한 실험에서 `호출 5건 / 차단 10건`으로
정상 동작을 확인했다.

**합산 일일 예산**: 대시보드 360~720회 + GitHub Actions 데이터 갱신 288회
≈ **650~1,000회/일** — 차단 지점(9,800)의 **7~10%** 수준이다.

**데이터 갱신 — 저장소가 원본이다.** Streamlit Cloud의 컨테이너
파일시스템은 휘발성이라 앱이 쓴 파일은 재시작 시 사라진다. 그래서 갱신
주체를 앱이 아니라 저장소로 둔다:
`.github/workflows/refresh-data.yml`이 6시간마다
`refresh_deploy_data.py`를 돌려 ① 최근 관측 창을 채우고 ② 적중률 로그의
대기 항목을 실측과 대조한 뒤, 결과를 main에 되커밋한다. Streamlit Cloud가
그 푸시를 감지해 자동 재배포하면서 새 데이터가 반영된다. 이 워크플로에도
`KMA_API_KEY` 시크릿이 필요하다(회당 약 72건, 하루 약 288건).

**공개 범위.** Community Cloud 앱은 기본이 공개 URL이다. 기상산업진흥법상
예보업 등록 대상이 아닌 범위로 유지하려면 앱 설정에서 뷰어 허용목록
(Private)으로 두는 것을 권한다 — 자세한 내용은 아래 "법적 범위" 항목 참고.

## 정직한 한계

본 프로젝트는 성능 달성보다 **설계 결함을 실험으로 규명하고 그 근거를 제시하는 과정**에 중점을 두었습니다. 아래 항목은 현 시점에서 확인된 한계와 그 원인 분석입니다.

### 1. 시뮬레이션 모달리티는 정보량이 정확히 0이었습니다 (→ 실측으로 교체 완료)

초기 Re축(합성 위성)과 Im축(MiniLM 텍스트)은 **Z축 수치에서 결정론적으로 생성한 시뮬레이션**이었습니다. 정보이론적으로 Z를 넘을 수 없는 구조인데, 실측이 이를 그대로 확인했습니다.

- **결정적 증거**: `deploy_ablation.py`에서 추론 시 Re축을 영벡터로 꺼도 출력이 **소수점까지 완전히 동일**했습니다(기여도 정확히 0).
- **게이트의 판단도 일치**: 게이트가 Re축에 배분한 가중치가 v4 시점에 **0.000**이었습니다. 모델이 스스로 "볼 가치가 없다"고 학습한 것입니다.

이후 **"단일 시점 스냅샷(Z)에서 유도할 수 없는 정보만 새 축에 담는다"**는 기준으로 재설계했습니다.

| 교체 | 이전 | 이후 | 결과 |
|---|---|---|---|
| Re축 | 합성 위성 이미지 | 11개 관측소 실측 IDW 공간보간장 | 게이트 배분 0.00 → **0.52**, 황사 F1 0.257 → **0.661** |
| Im축 | MiniLM 시뮬레이션 예보문 | 1·3·6h 전 대비 실측 변화량 | 게이트 배분 0.12 → 0.21 (F1은 일부 하락, 아래 참조) |

**Im축 교체는 성능이 오히려 떨어졌지만 그대로 유지했습니다.** MiniLM 대비 4개 F1 지표가 전부 낮습니다(강수 0.585→0.571, 폭염 0.880→0.862, 한파 0.765→0.730, 황사 0.671→0.602). 인코더 용량을 32→128로 키워도 회복되지 않아 "용량 부족" 가설은 기각됐습니다. 그럼에도 **"가짜 데이터를 입력으로 쓰지 않는다"**는 원칙을 성능보다 우선해 실측 유지를 택했고, 손해를 숨기지 않고 명시합니다. MiniLM은 실측 Z축의 재포장이라 완전한 가짜(합성 위성)와는 성격이 다르지만, 원칙의 일관성을 택했습니다.

부수 효과로 `sentence-transformers`(약 450MB) 의존성이 서빙 경로에서 완전히 사라져 배포 컨테이너 메모리가 **227.9MiB**(docker stats 실측)로 줄었습니다.

### 2. Gram-Schmidt 직교화는 이 도메인에서 손해였습니다

논문은 검색 태스크에서 축 독립성(직교성)을 전제하지만, 실측(`ablation.py`)에서 직교화를 강제하면 성능이 하락했습니다. 네트워크가 자유롭게 학습한 Re-Im 상관도(0.48)가 오히려 회귀 성능에 기여하고 있었습니다 — 축 간 정보 공유가 강건성으로 작용하는 회귀 태스크와, 독립성이 곧 변별력인 검색 태스크는 다릅니다. 기본값은 `ORTHOGONALIZE = False`로 되돌렸습니다.

### 3. 정적 축 가중치는 무용한 축을 억제하지 못했습니다

학습 가능한 α/φ(log-parameter)는 정보가 없는 위성 축의 가중치를 오히려 키웠습니다(α 0.4→0.665). 원인은 두 가지: (a) 논문 기본값 자체가 위성 축을 1순위로 두는 초기화였고, (b) ResNet18(1,100만 파라미터)이 학습 표본(572개)을 그대로 암기해 훈련 손실 기준으로는 "가장 잘 맞는 축"으로 보였기 때문입니다. `ModalityGate`(균등 초기화 + 엔트로피 정규화 워밍업) + 인코더 축소(2.8만 파라미터)로 이 문제를 해결했습니다.

### 4. 1시간 예보는 무의미했습니다

1시간 후 기온은 퍼시스턴스(T(t+1)≈T(t))가 사실상 무적이라 어떤 모델도 유의미한 개선을 보여줄 수 없었습니다(+0.7%). 시계를 6시간으로 늘리자 시각(일주기) 특성과 축 융합이 실제로 기여하기 시작했습니다. 이 판단으로 `lead_hours = 6`을 확정했습니다.

> 위 +0.7%는 초기 30일 수집본(검증셋 1,709개) 기준 측정치입니다. 현행 3.5년 데이터셋(검증셋 약 66,000개)에서는 재측정하지 않았으므로, 시계 선택의 **근거로만** 인용하고 현행 성능 수치로 쓰지 않습니다.

### 4-1. 강수는 여전히 '상시 0mm' 기준선보다 나쁩니다

가장 크게 실패한 지점이고, 가리지 않고 화면에도 표시합니다. **다만 2026-08-11 재학습에서 격차를 +0.8%까지 좁혔습니다**(이전 −19.3%). 강수는 대부분의 시각이 0mm라 **아무 계산 없이 "항상 0mm"라고만 답해도** MAE가 매우 낮게 나옵니다. 현행 모델의 강수 MAE는 그 기준선을 **넘지 못했습니다**.

원인은 구조적으로 추적됐습니다 — 극한기상 헤드가 3개(폭염→한파→황사)로 늘어나면서, 헤드들이 **하나의 공유 magnitude 표현(`s`)을 두고 경쟁**해 Hurdle의 무강수 억제력이 약해졌습니다(baseline 대비 −16.0% → −25.6%). `EXTREME_BCE_WEIGHT`를 1.0 → 0.3으로 낮춰 −19.3%까지 완화했고, 추론 후처리로 0.2mm 미만을 0으로 반올림해 남은 손해를 줄였습니다. **새 헤드를 추가할 때마다 강수 MAE를 반드시 재확인**하는 것이 이 프로젝트의 규약이 된 이유입니다.

강수는 MAE보다 "비가 올지 안 올지 맞혔나"가 실용 가치에 가깝고, 그 지표는 대시보드 '성능 검증' 탭의 강수 적중률(0.1mm 기준 비/무비 판정 일치)로 따로 봅니다.

> 기준선 수치는 학습 시 계산은 하지만 체크포인트에 저장하지 않던 버전이라, 현행 체크포인트로는 화면에서 직접 비교하지 못합니다. `train.py`에 `val_temp_naive_mae`·`val_precip_naive_mae` 저장을 추가해 다음 재학습부터는 대시보드에 증감으로 자동 표시됩니다.

### 5. 이 프로젝트 자체의 디버깅 과정에서 잡은 실제 버그들

- `torch.clamp(x, 0, 200)`이 x<0에서 gradient가 정확히 0이 되어, 강수 예측 헤드가 전 샘플 음수로 수렴한 뒤 영구히 학습 정지 (`softplus`로 교체)
- 기온 손실(σ²≈수십 규모)이 강수 손실(O(1))을 1000배 압도해 강수 헤드가 사실상 학습되지 않음 (분산 정규화)
- baseline을 검증셋이 아닌 전체 데이터에서 계산해 표본 불일치로 인한 허위 "개선"이 발생 (검증셋 동일 표본으로 수정)
- 다중 관측소 확장 시 관측소 경계에서 서울 관측값과 부산의 6시간 후 관측값이 우연히 페어링될 수 있는 경로 존재 (관측소 코드 일치 조건 추가로 원천 차단)
- 테스트 스크립트가 실패 항목을 출력만 하고 종료 코드 0을 반환해, **CI가 어떤 항목이 깨져도 항상 초록불**이었음 (`sys.exit(0 if n_pass == n_all else 1)` 추가). 테스트를 CI에 붙이는 것과 CI가 테스트 결과에 반응하는 것은 별개였습니다.

### 6. 논문의 '위상각'은 이 구현에서 수학적으로 퇴화합니다

Phase 3-6에서 논문의 위상 필터(θ<30°/30–80°/>80°)를 경보 게이트의 상태로 쓰려고 θ를 실제로 계산해 봤더니, 이 아키텍처에서는 정보가 없는 값이었습니다.

```
θ = atan2(‖w_im·v_im‖, ‖w_re·v_re‖)
  세 인코더가 모두 F.normalize 출력 → ‖v‖ = 1
  ∴ θ = atan2(w_im, w_re)          ← 게이트 배분의 재표현일 뿐
```

`test_phase36.py` T1에서 두 값의 최대 차이가 **1.19e-07**로 확인됩니다. 즉 θ는 축 자체의 표본별 정보를 전혀 담지 못하고, 게이트 가중치를 극좌표로 바꿔 쓴 값입니다. 검색 태스크(논문 원본)에서는 축 임베딩의 노름이 자유로워 θ가 의미를 갖지만, 단위 정규화를 쓰는 이 회귀 구현으로는 그 개념이 이전되지 않습니다. 표본별 축 정보는 축 간 코사인(`cos(Re,Im)` 등, 표준편차 0.109)에만 남아 있어 상태에는 그쪽을 함께 넣었습니다.

### 7. PPO는 이 규모에서 지도학습 기준선을 이기지 못했습니다

경보 문제는 RL을 쓸 근거를 의도적으로 갖추도록 설계했습니다 — 비대칭 비용(미탐지 −20 : 오경보 −1), 이산 행동, 그리고 **경보 피로**(최근 경보가 쌓이면 다음 오경보 비용이 커짐)입니다. 피로 항 덕분에 보상이 과거 행동에 의존하므로 이 문제는 밴딧이 아니라 진짜 MDP이고, `test_phase36.py` T5가 이를 수치로 확인합니다(동일 관측·동일 행동인데 이력에 따라 보상 −1.00 vs −2.00).

그런데도 4-fold 교차검증에서 PPO는 졌습니다(−0.173 vs 지도학습 −0.112, 고정 임계값 −0.139). 조건은 대칭으로 맞췄습니다 — 모든 방법이 같은 7개 관측소로 적합하고, 같은 2개 관측소에서 임계값·반복을 고르고, 나머지 3개에서만 평가했습니다.

진 이유는 두 가지로 봅니다.

1. **MDP 구조가 실재하지만 크기가 작습니다.** 최적 경보율이 5~9% 수준인데, 이 구간의 정상상태 피로는 약 0.5라 오경보 비용 배수가 1.5배에 그칩니다. 순차적 결합이 존재는 하되 지배항이 아니라, PPO가 얻을 수 있는 이득 자체가 얇습니다.
2. **표본이 부족합니다.** 이벤트가 전체 214개(적합 겹당 약 130개)입니다. 지도학습은 표본마다 정답 라벨을 직접 받지만 PPO는 같은 신호를 표집된 리턴에서 스스로 찾아내야 합니다. 이 격차가 위 1의 얇은 이득을 덮습니다.

부수적으로 얻은 결과가 하나 더 있습니다. 상태에 게이트 가중치·θ·기압·습도를 넣은 조건(full)은 적합 보상이 −0.132로 가장 좋은데 검증은 −0.200으로 가장 나빴습니다(격차 0.069). 게이트 입력에 위도·경도가 포함돼 있어(`train.record_to_vec` 인덱스 10·11) 이 특성들이 사실상 **관측소 식별자**로 작동했기 때문입니다. 지점 불변 물리량만 남기자 격차가 0.014로 줄었습니다 — 관측망 공백 지대 예측을 표방하는 시스템에서 정책이 지점을 외우고 있었다는 뜻이라, 이 프로젝트 문제의식 자체에 직접 걸리는 결함이었습니다.

### 8. 시간 분할 검증이 이 데이터에서는 불가능했습니다

처음에는 관측소별로 앞 70%를 학습, 뒤 30%를 검증으로 두려 했습니다. 그런데 수집 구간(2026-07-08 ~ 08-07)이 장마 종료 경계를 가로지릅니다.

| 구간 | 평균 강수 | 돌발 강수 이벤트 |
|---|---|---|
| 앞 70% (7/8~7/29, 장마) | 0.695 mm | 212개 / 5,973 (3.55%) |
| 뒤 30% (7/29~8/7, 폭염) | **0.000 mm** | **2개 / 2,573 (0.08%)** |

검증 구간에 비가 아예 오지 않아 평가 자체가 성립하지 않습니다. 관측소를 3개씩 4묶음으로 나눈 교차검증으로 바꿔, 모든 fold가 같은 기간을 공유하게 하고 8,546쌍 전량이 정확히 한 번씩 검증셋이 되도록 했습니다. 30일 수집으로는 계절 일반화를 측정할 수 없다는 뜻이며, 이는 데이터 기간을 1년 이상으로 늘려야 풀리는 문제입니다.

## 재학습이 필요한가 — 자동화 검토

**실시간 관측은 모델을 다시 학습시키지 않습니다.** 화면의 모델은 고정된
체크포인트이고, 매 5분 갱신되는 관측값은 두 가지로만 쓰입니다.

1. **추론 입력** — 지금 이 순간의 관측값(+ 이웃 11곳 + 과거 1·3·6h)을 넣어
   +6시간 뒤를 계산한다. **가중치는 건드리지 않는다.**
2. **적중률 기록** — 출력값을 로그에 남기고 6시간 뒤 실측이 확정되면 대조한다.
   **이 대조 결과도 모델을 바꾸지 않는다** — 순수 사후 모니터링이다.

온라인 학습(관측 1건마다 즉시 가중치 갱신)은 **의도적으로 넣지 않았습니다**.

| 근거 | 내용 |
|---|---|
| 표본 밀도 | 관측소당 신규 표본이 **시간당 1건**. 배치 1에폭이 보는 수만 건의 그레디언트 평균과 달리, 1건짜리 업데이트는 노이즈가 학습 신호보다 클 위험이 크다 |
| 재앙적 망각 | 최근 데이터에 맞춰 즉시 갱신하면 계절 패턴을 잊는다. 이를 막을 리플레이 버퍼·정규화 장치가 아직 없다 |
| 재현성 | 배치 재학습은 "이 체크포인트 = 이 데이터 + 이 코드"를 그대로 감사·재현할 수 있다. 온라인 학습은 매 순간 가중치가 달라 같은 상황을 재현하기 어렵다 |

### 그러면 주기적 재학습은 필요한가 — 필요합니다

기후 데이터는 **계절 순환**이 지배적이고, 학습셋에 없는 계절 구간은 외삽이
됩니다. 실제로 이 프로젝트는 초기 30일 수집(2026-07~08, 장마→폭염 경계)에서
**검증 구간에 비가 아예 오지 않아 평가 자체가 성립하지 않는** 문제를 겪었고
(아래 [한계 8](#8-시간-분할-검증이-이-데이터에서는-불가능했습니다)), 데이터를
3.5년으로 늘려서야 해결했습니다. 따라서 재학습 주기는 **분기~반기 단위**가
합리적입니다(월 단위는 신규 표본이 전체의 2% 남짓이라 이득이 얇습니다).

### 자동화 가능 여부 — 부분 자동화가 현실적

| 단계 | 자동화 | 근거 |
|---|---|---|
| 신규 관측 수집 | ✅ **이미 자동** | `.github/workflows/refresh-data.yml` (6h 주기) + `refresh_deploy_data.py` |
| 극한기상 라벨 갱신 | ⚠️ **반자동** | '날씨 이슈별 데이터'·PM10은 포털에서 **수동 다운로드**해야 한다(API 미제공). `import_weather_issues.py`가 파싱은 자동화 |
| 재학습 실행 | ⚠️ **로컬 GPU 필요** | GitHub Actions 무료 러너는 GPU가 없다. 전체 학습 15~35분(GPU 기준) |
| 체크포인트 검증·배포 | ✅ 자동화 가능 | 재학습 후 검증 MAE·F1이 기존보다 나쁘면 배포를 막는 게이트를 CI에 넣을 수 있다 |

**권장 운영 방식**: 관측 수집만 상시 자동으로 돌리고(현재 구현됨), 분기마다
① 포털에서 라벨 CSV 수동 다운로드 → ② 로컬 GPU에서 `train.py` 실행 →
③ 검증 지표가 기존 체크포인트보다 나쁘지 않은지 확인 → ④ 체크포인트 커밋.
③은 이미 규약으로 강제돼 있습니다 — **재학습 전 반드시 백업**하고
(`numerical_trichef_vN_<이유>.pt`), 새 헤드를 추가할 때마다 강수 MAE를
재확인합니다.

```bash
python -m venv .venv
.venv\Scripts\activate      # Windows
pip install -r requirements.txt
```
