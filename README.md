# 환경 예보 (climate-forecast)

기상청 종관기상관측(ASOS) 지상 관측 자료를 이용해 6시간 후 기온·강수·극한기상 확률을 산출하는 3축 멀티모달(multimodal) 파이프라인이다.

논문 Tri-CHEF(*Complex-Hermitian Embedding Fusion for Korean Multimodal Retrieval*, Zenodo 프리프린트, DOI [10.5281/zenodo.20034370](https://doi.org/10.5281/zenodo.20034370))의 3축 융합 수식만을 차용하여, 원 논문의 대상 과제인 한국어 멀티모달 검색과는 상이한 기후 예측 과제에 적용한 실험이다. 이 과정에서 발견한 문제와 그 해결 과정을 코드 및 실험 결과로 기록한다.

> ⚠️ 본 저장소의 산출값은 모델 출력값이며, 기상청의 공식 예보·특보가 아니다.
> 기상산업진흥법상 예보업은 등록이 필요한 사업이므로, 실제 방재 판단의 근거로 사용해서는 안 된다.

### 출력값 추이

선과 막대는 최근 72시간의 실측값이며, 별 표시가 모델 출력값이다. 꽉 찬 별(★)은 +6시간, 속 빈 별(☆)은 +12시간 후 값이고 각자의 목표 시각에 찍히므로 리드타임 차이가 가로축 위치로도 드러난다. 두 점선은 모두 마지막 실측점에서 각각 뻗어나간다 — +12시간은 +6시간 출력값을 이어받아 계산하는 것이 아니라 같은 현재 관측값을 입력받는 독립된 체크포인트의 출력이므로, 별과 별을 잇는 형태로 그리면 연쇄 계산처럼 오해된다. 예측 대상은 기온·강수 두 항목이며, 습도·기압은 상황 판단을 위한 참고용 실측값으로 예측 대상이 아니다.

차트 아래 표는 기온·강수 출력값을 +6시간과 +12시간에 대해 동시에 보여준다. 각 값에는 현재 대비 변화량과 검증셋 평균절대오차(MAE)를 함께 적고, 현재 대비 상승은 빨간색·하강은 초록색으로 표시한다(2026-08-20 개편 — 종전에는 라디오 버튼으로 한 리드타임만 골라 보여줬으나, 두 값을 한 화면에서 바로 비교할 수 있도록 토글을 없앴다). 표의 열 제목 색은 차트의 별 색과 일치시켰다(주황 = 꽉 찬 별 = +6시간, 보라 = 속 빈 별 = +12시간) — 두 곳에 색을 따로 적어두면 한쪽만 바뀌어도 대응이 조용히 깨지므로 상수 하나로 묶어 관리한다.

네 소그래프의 세로축 눈금 간격은 표시 범위에 따라 자동으로 정해진다(2026-08-25). 종전에는 강수축만 0.5mm로 고정되어 있어 호우가 관측된 창에서는 눈금이 촘촘해 읽기 어려웠다. 축별 최소 간격(기온 0.5°C·강수 0.5mm·습도 5%·기압 1hPa)을 하한으로 두고, 범위가 넓어지면 1·2·5의 배수로 키워 눈금이 6개 안팎이 되도록 한다.

#### +12시간 2차 산출값(2026-08-18)

이 탭은 +6시간과 +12시간 출력값을 항상 함께 표시한다. `LEAD_HOURS`를 환경변수로 빼(`train.py`) 12/24/48시간을 각각 재학습해 성능 저하 곡선을 실측한 결과, +12시간은 절대오차 악화가 완만해(기온 MAE 1.30→1.66°C) 2차 산출값으로 채택했다. +24/48시간은 한파·황사 F1이 눈에 띄게 무너져 채택하지 않았다.

기준선(퍼시스턴스) 대비 개선폭(%)만으로 리드타임을 비교하면 안 된다는 것도 이 실측에서 확인했다 — 퍼시스턴스 자체가 일주기 위상에 따라 강해지거나 약해지므로(+24시간에서 특히 그렇다), 개선폭이 아니라 절대 오차로만 비교해야 한다.

**한파 F1은 `+6h`와 `+12h`가 이제 같은 방식(중첩 전이학습 + 조기종료)으로 개선됐다(2026-08-19 갱신).** `+6h`는 [중첩 전이학습 승격](#nested-transfer-promotion)을 거쳐 F1 0.499다. `+12h`도 같은 커리큘럼(`coldwave_nested_pretrain.py` → `head_decouple_finetune.py --calib-eval-split`)을 `numerical_trichef_12h.pt`를 시작점으로 독립 2회 실행했다 — 두 실행 모두 보정용 곡선이 정지 에폭 4를 골랐고(+6h는 에폭 3이었다, 리드타임이 다르니 정지점이 다른 것은 자연스럽다), 평가용 F1은 0.521·0.513으로 기준선(0.453) 대비 순이득 +0.068·+0.060을 기록했다. 두 지표 모두 근소하게 앞선 1회차를 채택했다.

`+12h` 후보는 게이트 4종을 재확인했다(`promote_checkpoint.py`는 `+6h` 경로에 고정돼 있어 개별 스크립트로 수동 실행). 계절 오탐 최악값 1.21%로 PASS(직전 배포본 5.41% WARN 대비 오히려 개선 — 커리큘럼이 25~30°C 구간의 잔여 오탐도 함께 줄인 것으로 보인다), 한파·폭염 단조성 모두 PASS(기온상관 −0.81·+0.31), 관측소 사각지대는 폭염·한파 PASS·황사만 기존과 동일한 구조적 WARN. `promote_checkpoint.py`가 없어 백업(`numerical_trichef_12h_before_coldwave_curriculum_20260819.pt`) 후 수동으로 배포했다 — `patch_extreme_metrics.py`로 극한기상 지표를 재계산하고(한파 F1 0.453→0.509) `probability_calibration_fit.py --apply`로 확률 보정도 재적합했다.

체크포인트는 `checkpoints/numerical_trichef_12h.pt`로 분리해 배포한다(+6h 배포 경로는 건드리지 않음). 확률 보정·임계값 재선정도 이 체크포인트에서 독립적으로 다시 수행했다(강수 t=0.182, 폭염 t=0.368, 한파 t=0.253, 황사 t=0.124 — 한파는 순이득 +0.0027로 0.01 기준 미달이라 원본 임계값을 곡선으로 옮긴 값을 그대로 쓴다).

**리드타임을 늘렸을 때의 저하 폭은 지표마다 다르다.** 두 배포 체크포인트를 같은 방식으로 재측정한 값이다(2026-08-25).

| 지표 | +6시간 | +12시간 | 변화 |
|---|---|---|---|
| 기온 MAE | 1.2966°C | 1.6643°C | +28.4% 악화 |
| 강수(기준선 대비) | −9.9% | **−25.1%** | **가장 크게 악화** |
| 폭염 F1 | 0.814 | 0.776 | −0.038 |
| 한파 F1 | 0.499 | **0.509** | +0.010(유지) |
| 황사 F1 | 0.191 | 0.192 | 사실상 동일 |

> 이 표의 두 열은 **관측소별 예외 5건을 추가하기 전(2026-08-29)** 같은 시점에 잰 값이다. 리드타임에 따른 저하 폭을 보는 것이 목적이라 한쪽 열만 갱신하면 비교가 성립하지 않으므로 함께 둔다. `+6h`의 현행 서빙 값은 위 [극한기상 분류 성능](#extreme-metrics) 표(폭염 0.817·한파 0.500·황사 0.190)를 본다.

한파가 +6시간을 근소하게 앞서는 것은 리드타임의 효과가 아니라 중첩 전이학습을 따로 적용한 결과다. 강수는 무강수 구간의 미세 출력이 리드타임과 함께 커지면서 격차가 두 배 이상 벌어진다 — 이 지표의 병목이 강수량 추정이 아니라 "0을 정확히 0으로 내는 것"이라는 [오차 분해](#metrics-and-breakdown) 결론과 같은 방향이다.

> 위 강수 행은 후처리 전(원본 모델 출력) 값이다. [강수 확률 게이팅](#precip-prob-gate)(2026-08-29)을 적용한 서빙 값은 +6시간 −3.8%, +12시간 −17.4%로 둘 다 좁혀진다 — 게이팅 임계값도 리드타임마다 따로 골랐다(+6시간 0.85, +12시간 0.75, `predict.py`의 `PRECIP_PROB_GATE_BY_LEAD`).

> 화면 캡션은 채택 당시(2026-08-18) "폭염·강수는 비슷하게 유지되나 한파·황사가 크게 흔들린다"고 적고 있었다. 2026-08-19 `+12h` 한파 승격 이후 이 서술이 실제와 어긋났으므로(한파가 오히려 앞서고, 가장 크게 무너지는 것은 강수다) 위 재측정값에 맞춰 정정했다.

**부수적으로 발견한 버그.** 이 작업 도중 `predict.py`의 `CHECKPOINT`가 환경변수를 전혀 읽지 않는 하드코딩 리터럴이었다는 걸 발견했다 — `train.py`의 `CHECKPOINT_PATH` 패턴과 겉보기엔 같아 보였지만 실제로는 달랐다. 이 때문에 이전 세션의 한파 헤드 중첩 극한사건 전이학습 실험이 의도한 대로 실행되지 않았다(상세: [기각한 시험] 절 아래 정정 기록). `predict.py`의 `CHECKPOINT`를 같은 환경변수 패턴으로 고쳐 원인을 제거했다.

### 극한기상(Extreme Weather)

폭염·한파 확률을 막대로, 판정 임계값(threshold)을 빨간 점선으로 함께 표시한다. 막대에 쓰이는 값은 확률 보정을 거친 뒤의 값이고 점선은 보정 공간에서 직접 고른 판정선이므로, 둘은 같은 척도 위에 있다(폭염 0.389, 한파 0.229 — 근거는 [확률 보정](#prob-calibration-sec) 참조). 각 확률이 어떤 정답 라벨(label)로 학습되었는지, 그 라벨의 한계는 무엇인지도 화면에 명시한다.

**황사 확률은 이 화면에 표시하지 않는다.** 정밀도가 11.6%(서빙 판정선 기준, 원본 확률 0.5 기준으로는 11.8%)에 불과하고 12개 관측소 중 6곳은 라벨 자체가 없어 채점된 적이 없기 때문이다(사유는 [극한기상 분류 성능](#극한기상-분류-성능그룹-분할-검증-서빙-판정선-기준) 참조). 헤드는 계산을 계속하되 화면에서만 제외하며, 화면이 그 사실과 사유를 직접 밝힌다.

호우(강수)도 이 탭에는 없다 — '출력값 추이' 탭의 강수량이 이미 강수 확률과 강수량 추정치를 곱한 값이라 중복이기 때문이다(허들 구조, '모델 구조' 탭 참조).

### 성능 검증

이 탭은 다섯 부분으로 구성된다 — ① 회귀 성능(기온·강수 MAE), ② 극한기상 분류 성능(정밀도·재현율·F1), ③ 관측소별 신뢰도 비교, ④ 확률 보정 상태(ECE), ⑤ 실시간 출력값의 적중률 실측 대조. ①~④는 검증셋에서 산출한 고정값이고, ⑤만 배포 이후 누적되는 온라인 기록이다.

회귀 MAE는 기준선(baseline, 학습을 거치지 않은 자명한 방법) 대비 개선율과 함께 표시한다. MAE는 절대값만으로는 성능의 좋고 나쁨을 판단할 수 없으며, 기준선과의 비교를 통해서만 의미를 가진다.

- 기온 1.30°C — 퍼시스턴스(T(t+6)≈T(t)) 대비 **+61.2% 개선**.
- 강수 0.167mm — 상시 무강수 예측 대비 **9.9% 미달**(체크포인트에 저장된 원본 회귀 출력 기준). 기준선에 미치지 못하는 지표도 은폐하지 않고 그대로 제시한다. 화면에 실제로 나가는 서빙 값은 [강수 확률 게이팅](#precip-prob-gate) 적용 후 −3.8%다.

> 2026-08-16 검증 방식을 변경했다. 이전 버전(기온 1.26°C·강수 0.9% 미달)보다 위 수치가 낮아 보이나, 모델 성능이 저하된 것이 아니라 검증 방식의 결함이 제거된 결과다. 상세 내용은 [정직한 한계 9번](#9-검증-분할이-일-단위-라벨을-누수시키고-있었다)을 참조한다.
> 같은 날, 연중 주기 특징(day-of-year feature)을 추가한 재학습(이하 A안)도 시도했다. 한파 헤드(head)가 기온에 반대로 반응하는 오류가 발견되어 원상복구했다. seed를 바꿔 4회 재학습한 결과 2회에서 같은 역전이 재현되었고, 집계 지표(F1·MAE)는 이 결함을 전혀 탐지하지 못했다 — "시도했다가 원복한 시험" 항목을 참조한다.

극한기상 평가에는 정확도(accuracy) 대신 정밀도(precision)·재현율(recall)·F1을 사용한다. 폭염 발생일이 전체의 1%에 불과한 경우, 항상 "폭염 아님"으로 답해도 정확도는 99%에 달하기 때문이다.

### 관측소별 신뢰도 분석 — 재현율×정밀도 캘리브레이션(Calibration)

위 표는 12개 관측소를 합산한 평균값이다. 한파 헤드의 오류를 수정하는 과정에서 "평균이 정상이어도 특정 관측소만 유의하게 낮을 수 있다"는 의문이 제기되어, 관측소별로 분해하여 검토했다.

방법은 다음과 같다. 관측소당 점 하나를 배치하며, x축은 재현율, y축은 정밀도다. 정확도 대신 이 두 지표를 사용하는 이유는 위와 동일하다 — 한파·황사처럼 양성(positive) 사례가 드문 사건은 accuracy로 평가하면 항상 높게 나와 변별력이 없다. 점에 부착된 십자 표시는 95% 신뢰구간(confidence interval, Wilson score)이다. 초기에는 시간 단위 표본을 독립 시행(independent trial)으로 가정해 계산했으나, 한파·폭염은 수일간 지속되는 사건이므로 동일 사건 내 연속된 시간 표본은 서로 독립이 아니다. 이를 무시하면 신뢰구간이 실제보다 좁게, 즉 과신(overconfidence)하게 산출된다. 따라서 "24시간 이내로 연속된 표본을 하나의 사건으로 묶은 수"를 유효 표본 크기(effective sample size)로 사용해 재계산했다(점 추정값인 재현율·정밀도 자체는 시간 단위를 그대로 사용한다 — 다른 표의 F1과 정의를 일치시키기 위함이다).

![관측소별 캘리브레이션 플롯](docs/images/calibration_plot.png)

**그림 읽는 법.** 왼쪽이 폭염, 오른쪽이 한파이며 점 하나가 관측소 하나다. 가로축은 재현율(실제 사건 중 잡아낸 비율), 세로축은 정밀도(사건이라 판정한 것 중 맞은 비율)이므로 **오른쪽 위로 갈수록 좋다**. 두 축이 상충한다는 점이 핵심이다 — 판정 임계값을 낮추면 재현율이 오르는 대신 정밀도가 떨어져 점이 왼쪽 위에서 오른쪽 아래로 이동한다. 어느 한쪽만 보면 임계값을 조작해 얼마든지 좋아 보이게 만들 수 있으므로 두 축을 동시에 본다. 점에 붙은 십자는 Wilson 95% 신뢰구간이며, **길이가 곧 표본 부족의 크기**다 — 한파 오른쪽 그림에서 십자가 화면 폭의 절반에 이르는 관측소들은 사건이 10건 내외뿐이라 점의 위치를 신뢰할 수 없다는 뜻이다. 왼쪽 위 상자는 관측소 코드와 이름의 대응표다.

실측 결과 두 가지 이상 패턴이 발견되었으며, 두 원인 모두 규명했다(`station_anomaly_investigate.py`).

- **폭염: 부산만 유의하게 낮다 — 판정 기준 자체가 상이하다.** 나머지 11개 관측소는 재현율 82~91%, 정밀도 74~85%로 군집을 이루나, 부산(관측소 코드 159)만 재현율 71%, 정밀도 47%로 이탈한다. 원인 분석을 위해 오탐(모델이 폭염으로 예측했으나 공식 미판정)일 때의 기온을 확인한 결과, 부산은 오탐 시 평균 기온이 28.65°C로 부산 자신의 실제 폭염일 평균(27.38°C)보다 오히려 높았다. 대구는 반대로 오탐 시 기온(27.46°C)이 실제 폭염일 평균(28.58°C)보다 낮다 — 대구는 판정 경계 부근에서 혼동이 발생하는 통상적 패턴이며, 부산은 최고 기온일조차 공식적으로 폭염 미판정될 만큼 판정 기준 자체가 다르다. 모델은 관측소 구분 없이 공통 기준으로 학습되었으므로, 부산에서만 체계적으로 낮은 성능을 보인다.

  당시에는 재학습 없이 부산 전용 임계값(0.33)을 산출해 적용했다(순이득 +0.039). 그러나 2026-08-17 극한기상 헤드에 부호 표현을 추가한 이후 재검증한 결과, 부산 전용값의 순이득이 **−0.0033**으로 오히려 전역 0.5보다 나빴다(부산 정밀도도 47%에서 54.0%로 개선되었다). 검증을 통과하지 못한 예외는 두지 않는다는 규약에 따라 예외를 제거했다. 부산이 여전히 가장 낮은 관측소라는 사실 자체는 변하지 않았다 — 공식 판정 기준이 다른데 모델이 관측소 구분 없이 학습된다는 구조가 그대로이기 때문이다. 2026-08-19 한파 헤드 승격 후 재검증에서도 부산 폭염 예외는 다시 기각(순이득 −0.0033, 동일)됐지만, 전주 한파에서 새 예외가 채택됐다 — `STATION_EVENT_THRESH_OVERRIDES`는 더 이상 비어 있지 않다([아래 참조](#station-override-jeonju)).
- **한파: 대구·강릉도 결국 표본 부족이 원인이었다 — 시간 수는 착시였다.** 시간 단위 표본만 보면 대구 288건, 강릉 216건으로 남부·해안 관측소(24~192건)보다 많아 보였다. 그러나 24시간 이내 연속 표본을 하나의 사건으로 묶어 세면 대구 10건, 강릉 8건에 불과했다(춘천은 동일 기준으로 40건). 사건 수와 예측확률·미탐지율(miss rate)이 함께 변화했다(대구: 사건 10건, 평균확률 0.275, 미탐지율 73%; 춘천: 사건 40건, 평균확률 0.658, 미탐지율 32%) — 별도의 원인이 아니라 표본 부족이 원인이었음을 확인했다.

이 플롯은 `calibration_plot_diagnose.py`로 재생성하며, 체크포인트를 승격하면 `promote_checkpoint.py`가 자동으로 다시 그린다. 승격 절차를 거치지 않고 체크포인트만 바꾼 경우에는 직접 실행해야 한다 — 그림이 이전 모델 시점에 머무는 사고가 실제로 있었다(규약으로 고정한 경위는 [체크포인트 승격 자동화](#자동화-가능-범위--부분-자동화가-현실적이다) 참조).

### 모델 구조

모델 내부를 화면에서 직접 확인할 수 있게 한다. 구성은 다음과 같다.

- **이번 출력값의 축 배분** — 게이트가 이번 추론에서 3축에 나눈 가중치(합 100%). 고정 상수가 아니라 출력마다 재계산되므로, 관측소를 바꾸거나 다음 정시로 넘어가면 값이 달라진다.
- **3축이 각각 포착하는 정보** — 각 축이 답하는 질문, 입력 데이터, 그리고 "Z축만으로는 유도할 수 없는 이유".
- **3축 융합 수식(논문 Eq.1)** — 기호별 의미와 값의 범위, 연산 순서를 단계로 분해해 제시한다.
- **융합 벡터에서 분기하는 5개 예측** — 헤드 6개(기온·강수량·강수확률·폭염·한파·황사)가 같은 64차원 벡터를 어떻게 나눠 쓰는지. 강수는 헤드 2개의 곱이므로 헤드는 6개, 예측 항목은 5개다. 극한기상 헤드 3종만 부호 표현(`v_Z`)을 추가로 받는 이유도 함께 설명한다.
- **강수의 허들(Hurdle) 구조** — `ŷ = σ(z₁) × softplus(z₂)`의 각 항이 무엇을 맡는지.
- **실시간 관측의 용도와 재학습의 관계** — 실시간 관측은 추론 입력과 적중률 기록에만 쓰이며 가중치를 바꾸지 않는다는 점을 화면에서 명시한다.

## API 사용 시 유의사항

본 저장소를 직접 실행하려면 기상청 API 허브(apihub.kma.go.kr) 인증키가 필요하다. 아래 제약사항을 먼저 확인한다.

### 1. 호출량 — 산출값 1건당 API 15회, 화면 1회 갱신당 30회

| 구성 | 호출 수 |
|---|---|
| 대상 관측소 현재 관측 | 1 |
| 인접 11개 관측소(Re축 공간 보간장) | 11 |
| 대상 관측소의 1·3·6시간 전 관측(Im축 경향 벡터) | 3 |
| **산출값 1건 합계** | **15** |
| **화면 1회 갱신(+6h·+12h 각 1건)** | **30** |

**+12시간 2차 산출값을 추가한 뒤(2026-08-18) 화면 1회 갱신의 호출량이 15회에서 30회로 늘었다(2026-08-25 실측·정정).** 두 리드타임은 같은 관측을 입력으로 쓰지만 서로 다른 체크포인트를 통과하며, `predict()`가 호출마다 관측을 새로 조회하므로 같은 15건을 두 번 받는다. 관측소 1곳에 대해 `predict()`를 두 번 실행하고 계측한 값이 15 → 30이다. 문서가 이 변화를 반영하지 않은 채 "15회"로 남아 있었으므로 아래 예산 추정치를 함께 정정한다.

원리적으로는 첫 조회 결과를 두 체크포인트가 공유하면 30을 15로 되돌릴 수 있으나, 그러려면 관측 수집과 추론을 분리하도록 `predict()`의 시그니처를 바꿔야 한다. 실사용 호출량이 차단 지점의 10~17% 수준이라 현재는 착수 근거가 약하다고 판단해 그대로 두고, 사실만 명시한다.

이 비용은 접속자 수와 화면 갱신 횟수의 곱으로 증가한다. 대시보드 기본 갱신 주기가 5분이므로, 캐시가 없으면 관측소 1개만 열람해도 일일 8,640회에 도달해 차단 지점에 근접한다. 아래 3항의 관측 시각 단위 캐시가 이 곱셈을 끊는다.

### 2. 차단 이력 — 누적 약 9,800건

대량 수집 시도 시 누적 약 9,800건에서 차단되었다(2026-08-07 확인, 동시성 16 조건). 병렬화로 우회할 수 없는, 요청 수 자체를 기준으로 하는 제한으로 판단된다. 따라서 과거 데이터를 API로 수집하는 시도는 하지 않는다 — 기상자료개방포털의 파일셋(CSV 일괄 다운로드)을 사용한다.

| **관측 시각 단위 캐시** | 출력값을 (관측소, 관측 시각, 리드타임) 키로 캐시한다. ASOS는 매시 정각에 1회 관측하므로, 동일 정시 내 재조회는 동일한 값을 반환한다. 이에 따라 호출량이 갱신 주기·접속자 수와 무관하게 관측소당 시간당 30회(리드타임 2종 × 15회)로 고정된다 |

### 4. 외부 장애 — 배포 환경 발신 IP만 차단(2026-08-19)

2026-08-19 05:47 UTC부터 Streamlit Community Cloud 배포판에서 12개 관측소 조회가 전부 `ConnectTimeoutError`로 실패했다. HTTP 오류 응답이 아니라 **TCP 연결 자체가 성사되지 않는** 유형이다.

원인이 코드인지 외부인지를 **통제 대조**로 분리했다. 같은 시각·같은 엔드포인트·같은 인증키로 발신 환경만 다르게 두었다.

| 발신 환경 | 시각(UTC) | 결과 |
|---|---|---|
| GitHub Actions(Azure) | 06:51 | 성공 — 12개 관측소 수집·커밋 완료 |
| 로컬(가정용 회선) | 06:00대 | 성공 — 응답 0.25초 |
| Streamlit Cloud(AWS) | 05:47~11:06 | 전부 실패 |

API·인증키·호출량 모두 정상이며 배포 환경의 발신 IP 경로만 막혔다는 결론이다(호출량 84/3,000건, `weather_collector.py`는 2026-08-16 이후 무변경).

**기상청 문의 답변(2026-08-20)은 이 결론을 뒤집지 못했다.** 담당자는 "차단 이력이 없으며 직접 호출해보니 정상"이라 회신했으나, 그 확인은 기상청 자신의 네트워크에서 수행한 것이라 발신 경로가 다르다 — 위 통제 대조가 분리해낸 변수가 바로 발신 경로다. 코드로 대응할 수 있는 수단이 없으므로(재시도·타임아웃 조정으로 네트워크 차단을 우회하지 못한다) 저장소 실측 폴백을 유지한 채 시간 경과를 기다렸다. **장애는 이후 해소되어, 2026-08-25 현재 배포 화면은 실시간 관측으로 정상 동작한다.** 같은 증상(전 관측소 동시 타임아웃 + 호출 예산 여유 + 로컬은 정상)이 재현되면 다시 발신 IP 차단으로 판단하고 코드를 의심하는 데 시간을 쓰지 않는다.

**이 장애가 드러낸 것은 저장소 내부의 결함 세 가지였다.** 외부 원인이라도 그 상황에서 코드가 어떻게 행동하는지는 우리 책임이다.

1. **날조값을 실측처럼 표시** — 위 [발견한 실제 오류](#debug-found-bugs) 항목 참고. 저장소 실측으로 폴백하도록 고쳤다.
2. **조회 1회에 8분 정지** — 관측소당 34초(3회×10초+대기) × 12곳 + 과거 3시점 61초 ≈ 469초. 실패는 캐시되지 않아 재실행마다 반복됐다. 연결 실패는 관측소를 바꿔도 결과가 같으므로, 한 번 확인되면 쿨다운 동안 건너뛰도록 회로 차단기를 넣었다. 배포 환경 재현 실측 **469초 → 10.1초**.
3. **보조축이 통째로 무력화됨** — 이웃(Re축)·과거(Im축)를 `SUCCESS_LIVE`로만 받고 있어, 연결이 막히면 실측이 저장소에 있는데도 0/11·0/3이 되어 중립값으로 채워졌다. 실측 여부와 최신 여부를 분리해 판정하도록 고쳤다(같은 시각 스냅숏 조건은 유지 — IDW는 동시각 공간 분포를 전제하므로). 재현 실측 **11/11 · 3/3 복원**.

수정 후 배포 환경(디스크 캐시 없음 + 연결 불가)을 재현해 검증했다. 관측 시각을 조작하지 않으므로 화면은 "관측 10:00 → 목표 16:00"처럼 실제 시각을 그대로 표시하고, 몇 시간 전 관측인지도 함께 알린다. 저장소에 그 시각의 실측이 없으면 날조로 메우지 않고 자리표시자임을 명시한다(`FALLBACK_DEFAULT`, 화면은 오류 수준으로 경고하며 적중률 로그에도 기록하지 않는다).

### 5. 인증키 관리

인증키는 용도별로 분리하여 관리하며, 저장소에는 포함하지 않는다.

| 실행 환경 | 저장 위치 |
|---|---|
| 로컬 실행 | `.env`(gitignore 대상) |
| Streamlit Cloud 배포 | 앱 설정의 Secrets |
| GitHub Actions 자동 갱신 | 저장소 Secrets |

```toml
# Streamlit Secrets 형식 — 값은 반드시 큰따옴표로 감싼다.
KMA_API_KEY = "발급받은_키"
KMA_STN = "108"
```

> 따옴표를 생략하면 TOML 파싱이 실패하여 앱이 인증키를 읽지 못한다.
> 이 경우 화면은 대체값으로 정상적으로 표시되어 식별이 어렵다 —
> 사이드바의 API 호출 수가 0이면 이 상황을 의심한다.

**API허브는 자체 키 재발급 기능이 없다.** 유출 시 대응은 탈퇴 후 재가입뿐이며(포털 FAQ 확인,
2026-08-19), 재가입하면 활용신청 승인을 다시 받아야 해 그동안 서비스가 멈춘다. 이 비용이 크므로,
탈퇴 대신 **사용량 이상 감시**로 유출 여부를 상시 확인한다.

- `refresh_deploy_data.py`가 GitHub Actions 실행마다 실제 사용한 호출 수를 `cache/api_usage_daily.json`에
  누적 기록한다(날짜가 바뀌면 리셋). 재시작에 영향받지 않는다 — 저장소에 커밋되기 때문이다.
- 사이드바에 이 값과 "이 프로세스 시작 이후" 값을 함께 표시한다. 둘의 합이 **우리 시스템이 정상적으로
  쓴 호출량의 하한선**이다. 하한선이라고 적은 이유가 둘이다. 하나는 이 두 경로 바깥에서(다른 곳에서
  같은 키로) 쓴 호출은 여기 잡히지 않는다는 것이고, 다른 하나는 사이드바 값이 스크립트 순서상 +6시간
  추론 직후에 채워져 **그 뒤에 일어나는 +12시간 조회 15건이 첫 렌더링에서는 빠진다**는 것이다(다음
  재실행에서 따라잡는다). 어느 쪽이든 실제보다 작게 나오므로, 감시 목적으로는 안전한 방향이다.
- API허브 마이페이지의 "API 호출 현황"(실제 계정 전체 사용량, 매일 자정 초기화)과 비교한다 — 그
  값이 위 합보다 뚜렷이 크면 이 키가 다른 곳에서도 쓰이고 있다는 뜻이다. 이 저장소 코드는 계정
  전체 사용량을 직접 조회할 API가 없어(포털이 웹 화면으로만 제공), 자동 경보가 아니라 비교
  안내까지만 한다 — 최종 판단은 포털 화면을 사람이 확인해야 한다.

### 검증 방식 재정립(2026-08-16)

학습·검증 분할을 시각 단위 무작위 분할에서 날짜 단위 그룹 분할로 변경했다. 폭염·한파·황사 라벨은 (관측소, 날짜) 단위로 부여된다 — 특보가 발효된 날은 해당 일의 24개 시각 표본 전체가 동일한 라벨을 받는다. 그러나 기존 분할은 시각 단위 무작위였다. 확인 결과 판정 가능한 검증 표본의 100.00%가 학습셋과 동일 날짜 짝을 보유했다(양성 표본만 산정해도 100.00%). 모델이 해당 관측소·날짜의 정답을 학습 과정에서 이미 확인한 상태로 평가받고 있었다는 의미다. 날짜 전체를 한쪽에 배정하는 그룹 분할로 전환하자 극한기상 F1이 대폭 하락했다 — 모델 성능 저하가 아니라 부풀려진 값이 정상화된 결과다. 상세 경위와 수치는 [정직한 한계 9번](#9-검증-분할이-일-단위-라벨을-누수시키고-있었다)을 참조한다.

이하 결과는 모두 그룹 분할 방식으로 측정했다. 별도 보존한 v3~v7 및 3축 적용 효과 표는 무작위 분할로 측정한 이전 세대 기록이며, 비교 목적이 아니라 이력 보존 목적으로 유지한다.

### 시도했다가 원복한 시험 — 연중 주기 특징 추가(A안, 2026-08-16)

`partition_heterogeneity.py`로 분할 후보 축을 검토한 결과, 관측소(η²=0.00%)는 분할 근거가 없었으나 월(계절)은 입력 어디에도 포함되지 않은 상태였다. 시각 정보를 이미 아는 상태에서도 월 정보를 추가하면 기온 변화량(ΔT) 설명력이 6배 이상(+2.59%p) 증가했다. 이를 근거로 수치 입력에 연중 시각 sin/cos(day-of-year, 12→14차원)를 추가해 재학습한 결과 기온 MAE가 1.3551→1.2987°C로 개선되었다.

그러나 한파 헤드가 기온에 반대 방향으로 반응하는 오류가 발견되어 원상복구했다. 서울을 기준으로 다른 조건을 고정하고 기온만 15°C에서 33°C로 상승시키자, 한파 확률이 0.14에서 0.97로 상승했다(`coldwave_sensitivity_check.py`로 확인). 습도를 상승시켜도 한파 확률이 함께 상승했다 — 두 경우 모두 물리적으로는 반대 방향이 정상이다. 체크포인트 4종을 비교한 결과, A안 재학습 직후(헤드 디커플링(decoupling) 적용 이전)부터 이미 이 역전 현상이 존재했다. 원인은 한파 헤드 디커플링이 아니라 A안 재학습 자체다.

| 2026 | **역전**(여름 +0.382 · 가을 +0.460) | **1.2949°C** | −17.1% | 0.811 | 0.426 |
| *v9(12차원, 당시 배포본)* | *통과* | *1.3551°C* | *−17.9%* | *0.813* | *0.465* |

**4회 중 2회에서 역전이 재현되었다.** 한 번의 불운이 아니라 A안의 학습 자체가 불안정하다는 의미이며, 사전에 고정한 규칙에 따라 A안을 보류한다.

**집계 지표는 이 결함을 전혀 탐지하지 못한다.** 이것이 본 실험의 가장 중요한 결과다. 역전된 seed 42는 네 실행 중 한파 F1이 가장 높고(0.490), 배포 중인 v9(0.465)보다도 높다. 역전된 seed 2026은 기온 MAE가 가장 좋다(1.2949°C). 즉 F1·MAE만 기준으로 최선을 고르면 **물리적으로 가장 깨진 모델을 선택하게 된다.** 두 역전 체크포인트의 한파 F1(0.490 · 0.426)은 통과한 두 개(0.438 · 0.446)와 겹치는 범위에 있어, 지표 분포만으로는 구분 자체가 불가능하다.

역전의 형태는 계절에 국한된다. 겨울 구간에서는 정상으로 보이고 여름·가을의 고온부에서만 확률이 치솟는다 — seed 2026은 10월 30°C에서 한파 확률 0.90, 1월에는 기온과 무관하게 0.62~0.77로 실질적으로 무반응이었다. 근본 원인은 규명하지 못했다. 연중 시각 특징이 계절 신호를 제공하면서 한파 헤드가 기온 경로 대신 계절 경로에 의존하게 되고, 그 결합이 학습 초기값에 따라 불안정하게 형성되는 것을 유력한 가설로 본다.

**후속(2026-08-17) — 근본 원인은 계절이 아니라 부호였다.** 위 가설(계절 지름길)을 검증하려고 계절과 기온이 각각 확률을 얼마나 움직이는지 정량화했으나(`coldwave_pathway_check.py`), 계절 의존도가 역전본과 정상본에서 범위가 겹쳐 가설이 뒷받침되지 않았다. 같은 진단을 폭염 헤드로 확장하다가 더 심각한 결함을 발견했고 — 융합 수식이 부호를 없애 한겨울에 폭염 확률이 올라갔다 — 그 해결책(극한기상 헤드에 부호 표현 추가)이 한파 역전까지 함께 해소했다. 상세 내용은 [계절 오탐](#seasonal-false-alarm)을 참조한다. A안의 연중 시각 특징은 이 구성의 일부로 현재 배포에 포함되어 있다.

한파는 [중첩 전이학습 승격](#nested-transfer-promotion) 후 값이다. 아래 디커플링 항목의 0.458은 그 이전(2026-08-17) 기록이다.

<a id="coldwave-decouple"></a>

**한파 헤드 디커플링 재적용(2026-08-17).** 부호 표현을 넣은 승격 시점에는 한파 F1이 0.449였다. 직전 세대는 한파 헤드만 디커플링(decoupling — 트렁크 동결, 헤드만 미세조정)해 0.465를 기록했으나, 헤드를 미세조정하면 단조성을 다시 검증해야 해서 당시에는 제외했다. 그 검증이 승격 게이트(`promote_checkpoint.py`)로 자동화된 뒤 다시 적용해 **0.449 → 0.458**이 되었다. 트렁크를 얼렸으므로 기온 MAE(1.2966°C)·강수 MAE(0.1665mm)·폭염 F1(0.814)은 소수점 넷째 자리까지 변하지 않았고, 게이트 4종(계절 오탐 0.06%, 단조성 한파 −0.594·폭염 +0.558, 관측소 라벨 사각지대, 회귀 성능)을 모두 통과했다.

이 과정에서 미세조정 스크립트의 결함을 하나 발견했다. `head_decouple_finetune.py`가 최선 에폭의 가중치를 `state_dict()`로 담아두었는데, 이 함수는 파라미터 텐서를 복사하지 않고 그대로 돌려주므로 이후 에폭의 갱신이 그 텐서를 제자리에서 덮어썼다 — 즉 "최선 에폭을 저장한다"고 출력하면서 실제로는 항상 마지막 에폭을 저장하고 있었다. 최선 에폭으로 보고한 0.462와 저장본을 재계산한 0.458이 어긋나 드러났다(`patch_extreme_metrics.py`). `detach().clone()`으로 수정했다. 다만 재실행해 0.462를 취하지는 않았다 — 그 값은 보고에 쓰는 바로 그 검증셋에서 30개 에폭 중 최댓값을 고른 것이라 선택 편향이 섞인다. 30개 에폭이 모두 0.454~0.462로 이전 값 0.449를 넘으므로 이득 자체는 견고하며, 편향이 없는 마지막 에폭 값(0.458)을 채택했다.

임계값은 검증셋 절반(보정용)에서 산출하고 나머지 절반(평가용)에서 검증하는 절차를 따른다. 강수만 재산출값(t=0.83, 순이득 +0.101)을 채택했다. 폭염·한파·황사는 순이득이 각각 +0.004·+0.004·+0.002로 채택 기준(0.01)에 미달하여 기본값 0.5를 유지한다. 이 값들은 확률 보정 전(원본) 공간의 값이며, 화면 판정에 실제로 쓰이는 값은 [확률 보정](#prob-calibration)에서 따로 정한다.

황사는 본 표와 대시보드에서 제외했다. 정밀도가 11.6%에 불과해 황사로 판정한 결과 중 88.4%가 오탐이다(재현율 52.6%, F1 0.190). PM10 농도는 국외 장거리 수송의 영향이 지배적이나 본 모델의 입력은 국내 12개 지점의 기상 관측값에 한정되어, 구조적으로 판별 단서가 부족한 것으로 판단된다.

제외 근거는 정밀도만이 아니다. **12개 관측소 중 6곳(강릉·인천·청주·대전·부산·제주)은 황사 라벨이 존재하지 않는다** — PM10 관측망이 절반에만 있기 때문이다. 이 관측소들의 황사 출력은 학습에서도 평가에서도 한 번도 채점된 적이 없는데, 실제로는 임계값을 넘는 비율이 2~23%에 달한다(인천 23.4%). 화면에 표시했다면 검증된 적 없는 경보가 나갔을 것이다. 이 사각지대는 `station_coverage_check.py`로 상시 점검한다 — 폭염·한파는 12개 관측소 전부 라벨을 보유해 같은 문제가 없음을 확인했다.

헤드 자체는 유지되어 계산은 계속되나 화면에는 표시하지 않는다.

### 계절 오탐 — 융합 수식이 부호를 없앤다(2026-08-17)

본 저장소에서 발견한 가장 심각한 결함이며, 집계 지표로는 **구조적으로 탐지되지 않았다.**

이전 배포본(12차원)의 폭염 헤드가 한겨울에 작동했다. 합성 입력이 아니라 그 시각의 실제 이웃 관측(Re축)·실제 경향(Im축)을 그대로 사용한 실측이다.

| 실제 기온대 | 표본 | 폭염 확률 평균 | 0.5 초과 비율 |
|---|---|---|---|
| −15°C 이하 | 809건 | 0.73 | **85.7%** |
| −15~−10°C | 6,515건 | 0.54 | 57.4% |
| 30°C 이상(정상 동작) | 54,275건 | 0.80 | 85.7% |

**원인은 융합 수식이다.** `s = √((w·v)²)`는 제곱을 거치며 부호를 없애므로, 모든 헤드는 `|편차|`만 볼 뿐 위로 벗어났는지 아래로 벗어났는지 알 수 없다. 극단적 저온의 큰 편차가 극단적 고온과 같은 크기로 들어온다. 회귀 기온 헤드가 퍼시스턴스 잔차 구조를 쓰는 이유와 정확히 같은 문제이며(위 '아키텍처' 참조), 분류 헤드에서도 같은 원인이 작동한다는 것을 오랫동안 인지하지 못했다.

**F1 0.813에 잡히지 않은 이유**: 폭염 라벨은 공식 특보 기록이 있는 표본에서만 채점한다. 겨울 표본은 마스크가 0이므로 **애초에 채점 대상이 아니다.** 지표가 구조적으로 관측하지 못하던 구간이며, 이를 드러내려면 라벨과 무관하게 기온대별로 확률을 직접 보는 수밖에 없었다(`seasonal_falsealarm_check.py`).

**해결**: 극한기상 헤드 3종의 입력을 `s` 단독에서 `[s, v_Z]`로 확장했다. `v_Z`(정규화된 Z축 임베딩)는 제곱을 거치지 않아 부호가 살아 있다. 원본 수치 벡터를 직접 넣지 않은 이유는 거기에 위도·경도가 포함되어 헤드가 관측소를 암기할 통로가 되기 때문이다(Phase 3-6 PPO에서 실제로 발생한 문제). 회귀·강수 헤드는 변경하지 않았다.

| 체크포인트 | 겨울 폭염 오탐 | 여름 한파 오탐 | 최악값 |
|---|---|---|---|
| 이전 배포본(12차원) | 85.7% | 0.84% | **85.7%** |
| 연중 시각만 추가(14차원) | 0.00% | 11.8% | **11.8%** |
| 14차원 + 부호 표현 | 0.00% | 0.04% | **0.08%** |
| ＋한파 헤드 디커플링(2026-08-17) | 0.00% | 0.01% | 0.06% |
| **현행(＋중첩 전이학습 승격, 2026-08-19)** | **0.00%** | **0.01%** | **0.014%** |

연중 시각 특징만 추가해도 겨울 폭염은 해소되나 여름 한파 오탐이 남았다. 두 극단을 모두 잡은 것은 부호 표현을 넣은 이후다. 한파 헤드 디커플링([위 항목](#coldwave-decouple))은 오탐을 더 낮추면서 F1을 올렸다.

부수적으로 부산 폭염 전용 임계값이 불필요해져 제거했다 — 상세 근거는 [관측소별 신뢰도 분석](#관측소별-신뢰도-분석--재현율정밀도-캘리브레이션calibration)에 있다. 관측소별 예외가 전부 없어진 것은 아니다: 전주 한파는 검증을 통과해 적용 중이다([아래 참조](#station-override-jeonju)).

### 기각한 시험 — 강수 헤드 부호 표현 · 헤드 드롭아웃(2026-08-17)

극한기상 헤드에 부호 표현을 준 조치가 강수까지 개선한 것을 근거로, 두 가지 후속 변경을 각각 독립적으로 시험했다. 한 번에 함께 넣으면 결과가 나빠졌을 때 원인을 가릴 수 없으므로 조건을 하나씩만 바꿨다. 나머지 조건(seed 7, 그룹 분할, 배치 1024, 학습률 1e-3)은 현행과 동일하다.

아래 표의 기준선은 **시험 당시 배포본**(부호 표현 적용, 디커플링 전)이다. 세 시험 모두 이 기준선에서 조건 하나씩만 바꿔 재학습했으므로, 이후 승격한 디커플링 결과와 섞지 않는다.

| 지표 | 시험 당시 배포본 | A: 강수 헤드 부호 표현 | B: 헤드 드롭아웃 0.1 | C: 한파 헤드 전용 드롭아웃 0.1 |
|---|---|---|---|---|
| 기온 MAE | **1.2966°C** | 1.4104°C | 1.3120°C | 1.3053°C |
| 강수(기준선 대비) | **−9.9%** | −20.7% | −12.7% | −19.8% |
| 폭염 F1 | **0.814** | 0.801 | 0.809 | 0.802 |
| 한파 F1 | 0.449 | 0.415 | 0.472 | **0.460** |
| 계절 오탐 최악값 | **0.08%** | — | 38.8%(FAIL) | **0.70%(PASS)** |

**A — 가설이 기각되었다.** 강수 헤드가 공유 표현 경쟁에서 벗어나면 강수가 더 좋아질 것으로 예상했으나, 개선하려던 강수가 가장 크게 악화되었다(−9.9% → −20.7%). 극한기상 헤드에서 통했던 조치가 강수 경로에는 통하지 않는다. 강수량은 부호가 있는 양이 아니므로(항상 0 이상), 극한기상에서 부호 표현이 해결했던 문제 자체가 강수에는 존재하지 않았던 것으로 해석한다.

**B — 지표만 보면 채택할 뻔했다.** 한파 F1이 0.472로 디커플링 없이 기록한 최고값이었다. 드롭아웃이 정규화로 작용해 사건이 8~40건뿐인 희소 헤드의 과적합을 억제한 것으로 보인다. 그러나 승격 게이트에서 **계절 오탐 38.8%로 FAIL**했다 — 겨울 폭염 오탐이 되살아났다(−15°C 이하 809건 중 38.8%가 판정선 초과).

원인은 드롭아웃이 무엇을 끄는지 생각하면 분명하다. 겨울 폭염 오탐을 해결한 것은 헤드에 부호 표현(`v_Z`)을 넣은 조치인데, 헤드 드롭아웃은 그 경로의 유닛을 무작위로 끈다. **결함을 고친 바로 그 경로를 학습 중에 반복적으로 차단한 셈**이다. 두 변경은 함께 쓸 수 없다.

이 사례는 승격 게이트를 만든 이유를 그대로 보여준다 — F1·MAE만 보았다면 한파 개선을 근거로 채택을 검토했을 것이고, 겨울이 되어서야 결함을 발견했을 것이다.

**C — 격리는 성공했으나 강수에서 예상 밖 부작용이 나왔다.** B에서 드러난 원인 분석에 따라 드롭아웃을 한파 헤드에만 적용해(`COLDWAVE_DROPOUT=0.1`, 폭염·황사 헤드는 미적용) 폭염의 부호 경로를 건드리지 않도록 격리했다. 의도한 효과는 그대로 나왔다 — 계절 오탐 0.70%로 승격 게이트 통과, 단조성도 두 헤드 모두 개선되었고, 한파 F1도 0.460으로 디커플링 없이 기록한 두 번째로 높은 값이다. 그러나 강수가 −19.8%로 B(−12.7%)보다도 나빠졌다. 헤드별 입력을 분리해도 트렁크와 게이트는 여전히 공유되므로, 한 헤드만 드롭아웃을 걸어도 그 경사(gradient)가 공유 표현을 거쳐 강수 경로까지 흔든 것으로 추정한다. 한파 F1 개선(+0.011)이 강수 악화(약 10%p)를 정당화하지 못한다고 판단해 **채택하지 않는다**. 코드는 `COLDWAVE_DROPOUT` 환경변수로 재현 가능하게 남기되 기본값은 0(끔)이다. 헤드 드롭아웃 계열(B, C)은 이것으로 결론 내리며, 같은 방향의 재시도는 트렁크·게이트 공유 문제를 먼저 해소하지 않는 한 근거 없이 다시 하지 않는다.

### 기각한 시험 — 황사 헤드 제외(2026-08-17)

황사는 정밀도 11.8%로 실용 수준에 미달해 화면에서 이미 제외돼 있고, 12개 관측소 중 6곳은 라벨이 존재하지 않아 채점된 적도 없다. 한편 "헤드가 늘면 강수가 나빠진다"는 것은 이 저장소가 이미 확립한 사실이다(`EXTREME_BCE_WEIGHT`를 1.0→0.3으로 낮춰 강수를 −25.6%→−19.3%로 개선한 실측). 그렇다면 **쓰지도 않는 헤드를 손실에서 빼면 나머지가 좋아질 것**이라는 가설이 선다. 조건을 하나만 바꿔(`DUST_LOSS_WT=0`, seed 7·그룹 분할·나머지 동일) 확인했다.

| 지표 | 현행 배포 | 황사 헤드 손실 제외 | 판정 |
|---|---|---|---|
| 기온 MAE | **1.2966°C** | 1.3971°C | 악화 |
| 강수(기준선 대비) | **−9.9%** | −22.8% | **크게 악화** |
| 폭염 F1 | **0.814** | 0.777 | 악화 |
| 한파 F1 | **0.458** | 0.328 | **크게 악화** |

**가설이 정반대로 기각됐다.** 네 지표가 모두 나빠졌고, 특히 개선을 기대했던 강수가 −9.9%에서 −22.8%로 두 배 이상 벌어졌다.

기전은 게이트 배분에서 드러난다(`gate_behavior_check.py`, 두 모델을 같은 검증 표본에서 측정).

| 축 | 현행 배포 | 황사 헤드 제외 |
|---|---|---|
| Re(공간보간장) | **48.4%** | **20.4%** |
| Im(시간경향) | 20.8% | 46.0% |
| Z(수치) | 30.7% | 33.6% |

**황사 헤드가 Re축 학습을 견인하고 있었다.** 황사는 국외 장거리 수송이 지배하는 광역 현상이라 주변 지점의 공간 분포가 주된 단서이고, 실제로 Re축을 합성 위성에서 실측 IDW 보간장으로 교체했을 때 가장 크게 개선된 지표가 황사 F1이었다(0.257→0.661). 그 손실 항이 사라지자 게이트가 Re축을 버렸고(48%→20%), Re축 활용이 무너지면서 기온·강수·폭염·한파가 함께 나빠졌다.

따라서 "헤드가 늘면 강수가 나빠진다"는 서술을 정교화한다. **헤드 추가가 항상 손해인 것이 아니라, 공유 표현을 두고 경쟁하는 헤드는 손해이고 특정 축의 학습을 견인하는 헤드는 이득이다.** 황사 헤드는 후자이며, 화면에 표시하지 않더라도 **유지한다**.

### 기각한 시험 — 강수 amount 헤드 Gamma NLL(2026-08-18)

습윤 표본(강수≥WET_THRESH, n=17,015)의 강수량 분포를 정규·감마·로그정규에 적합해 콜모고로프-스미르노프(KS) 통계량을 비교한 결과 로그정규가 가장 적합했다(정규 0.294 · 감마 0.111 · 로그정규 0.066 — 값이 작을수록 적합). 현재 amount 헤드는 대칭 손실(MSE)로 학습되어 있어, 강수량처럼 오른쪽 꼬리가 두꺼운 분포에서는 호우 분위수를 구조적으로 과소예측할 수 있다는 가설을 세웠다. amount 헤드를 Gamma 분포 모수(μ, α) 회귀로 바꾸고 습윤 표본에만 NLL 손실을 적용해(`PRECIP_GAMMA_NLL=1`, 나머지 조건은 현행과 동일) 검증했다.

| 지표 | 현행 배포(MSE) | Gamma NLL |
|---|---|---|
| 기온 MAE | 1.2966°C | 1.2562°C(오차범위 내) |
| 강수(기준선 대비) | **−9.9%** | **−147.5%** |

**가설이 정반대로, 그것도 크게 기각됐다.** 강수 MAE가 상시 0mm 예측(가장 단순한 기준선)보다도 2.5배 나빠졌다. 원인은 최종 출력이 여전히 `rain_prob × μ`(hurdle 분류 확률과 amount 의 곱)로 결합된다는 데 있다. 기존 MSE 학습에서는 amount 헤드가 이 곱셈 구조 자체에 맞춰 학습됐다 — `rain_prob`가 불확실한(0과 1 사이인) 구간에서 곱의 오차를 줄이려면 amount 가 작은 값을 내는 편이 유리하므로, amount 헤드가 암묵적으로 위축(shrinkage)되어 있었고 그 위축이 우연히 곱의 MAE를 낮추는 방향으로 작동했다. Gamma NLL로 μ를 `rain_prob`와 무관하게 "편향 없는" 조건부 평균(습윤 표본 평균 2.42mm)에 맞추자 이 보정이 사라졌고, `rain_prob`가 완벽하지 않은 대다수 구간에서 곱셈값이 실측을 크게 벗어났다.

Gamma·CSGD류 확률적 헤드를 이런 hurdle 구조에 넣으려면 평가 지표를 MAE가 아니라 CRPS로, 점추정도 단순 곱셈이 아니라 혼합분포의 결정이론적으로 맞는 값(예: 중앙값)으로 다시 설계해야 한다. 이는 `forward()`가 스칼라 `precip_pred`를 그대로 반환해야 하는(기존 호출부 보존) 현재 제약을 벗어나는 더 큰 아키텍처 변경이라 이번 실험 범위에서는 시도하지 않았다. 코드는 `pipeline_model.py`/`train.py`에 `precip_gamma_nll` 인자로 남아있으며 기본값 False다.

### 확률 보정 — 표시된 확률이 실제 빈도와 일치하는가(2026-08-16)

위 지표는 "얼마나 잘 맞히는가"를 측정하나, "모델이 산출한 확률이 실제 발생 빈도와 일치하는가"는 별개의 문제다. 본 프로젝트에서 '보정(calibration)'이라는 용어는 그동안 판정 임계값 선정(`threshold_validation.py`)과 관측소별 정밀도-재현율 산점도(`calibration_plot_diagnose.py`)를 가리켰으며, 확률 자체의 정합성은 한 번도 측정한 적이 없었다. 그럼에도 대시보드는 이 확률을 막대로 그대로 노출하고 있었다.

검증셋(그룹 분할, 276,116개 표본)에서 신뢰도 곡선(reliability diagram)을 측정한 결과, 네 헤드 모두 체계적으로 과신(overconfidence)했다.

![확률 보정 상태](docs/images/probability_calibration.png)

**그림 읽는 법.** 열 하나가 헤드 하나다. 윗줄은 신뢰도 곡선(reliability diagram)으로, 가로축은 모델이 낸 확률, 세로축은 그 확률을 낸 표본들에서 사건이 **실제로** 일어난 빈도다. 두 축이 같은 척도이므로 정사각형으로 그렸고, 회색 대각선(y = x)이 "말한 확률과 실제 빈도가 일치하는" 완전 보정 상태다. **곡선이 대각선 아래에 있으면 과신**(말한 것보다 덜 일어남), 위에 있으면 과소평가다. 네 헤드 모두 대각선 아래에 있었다. 점의 크기는 그 구간의 표본 수이며, 오른쪽 끝처럼 표본이 적은 구간은 빈도가 크게 요동치므로 크기를 함께 보아야 과대해석하지 않는다.

범례와 설명 상자는 첫 열(강수)에만 두었다 — 네 패널의 기호가 모두 같으므로 열마다 반복하면 곡선을 가린다.

붉은 점선은 **실제 양성률**, 즉 전체 표본에서 사건이 실제로 일어난 비율이다. 아무 정보 없이 늘 이 값만 답할 때 그려지는 수평선이므로, 곡선이 이 선에서 위아래로 크게 벌어질수록 모델이 위험한 시각과 그렇지 않은 시각을 실제로 가려내고 있다는 뜻이다. 보정은 이 변별력은 그대로 둔 채 세로 위치만 대각선 쪽으로 옮기는 작업이다.

아랫줄은 각 확률 구간의 표본 수를 로그 눈금으로 표시한다. 윗줄의 곡선이 어느 구간에서 신뢰할 만한지를 판단하는 근거이며, 네 헤드 모두 표본이 0~0.1 구간에 압도적으로 몰려 있다. ECE가 표본 수로 가중평균한 값이라 낮게 보이는 이유가 여기에 있고, 정작 화면에 노출되는 중·고확률 구간의 어긋남은 MCE로 보아야 한다.

| 사건 | 보정 전 ECE | 보정 후 ECE | 보정 전 MCE | F1 변화 |
|---|---|---|---|---|
| 폭염 | 0.0340 | **0.0048** | 0.189 | 0.8144 → 0.8144 |
| 한파 | 0.0397 | **0.0015** | 0.354 | 0.5054 → 0.5071 |
| *강수* | *0.1719* | *0.0017* | *0.573* | *0.4981 → 0.4981* |
| *황사* | *0.1196* | *0.0006* | *0.785* | *0.1889 → 0.1894* |

보정 전 열은 검증셋 전체(`probability_calibration_check.py`, 위 그림과 동일 근거)에서, 보정 후 열과 F1은 보정용/평가용을 분리한 평가용 절반(`probability_calibration_fit.py`)에서 측정했다 — 표본이 달라 소수점 셋째 자리에서 차이가 날 수 있다.

화면에 확률로 표시되는 것은 폭염·한파 두 가지다. 강수는 확률이 아니라 mm로 표시되고, 황사는 앞서 밝힌 사유로 화면에서 제외했다 — 아래 두 행은 측정 기록으로만 남긴다.

ECE(Expected Calibration Error)는 구간별 "표시 확률 − 실제 빈도"의 차이를 표본 수로 가중평균한 값이며, MCE(Maximum Calibration Error)는 그 최댓값이다. 한파의 ECE가 낮아 보이는 것은 표본 대부분이 0~0.1 구간에 몰려 있기 때문이며, 화면에 실제로 노출되는 중·고확률 구간은 MCE가 보여주듯 크게 어긋나 있었다 — 이전 배포본에서 60~70%로 표시되던 구간의 실제 발생 빈도는 27%였다. 위 표는 현행 체크포인트를 기준으로 재적합한 값이다(재학습 시마다 곡선을 다시 적합해야 한다).

**원인은 결함이 아니라 설계상의 대가다.** 한파처럼 양성이 6%뿐인 사건은 모델이 "항상 아님"으로 답하는 자명해로 수렴하기 쉬워, 학습 시 양성 표본의 손실에 가중치(`pos_weight`)를 부여한다. 이것이 재현율을 확보하는 대신 확률을 위로 밀어올린다. 실제로 보정 오차의 크기 순서가 이 가중치의 크기 순서와 정확히 일치했다(폭염 3.06 → 한파 13.63 → 강수 15.60 → 황사 35.98).

재학습 없이 등온 회귀(isotonic regression)로 되돌렸다(`probability_calibration_fit.py`). 절차는 임계값 선정과 동일하다 — 검증셋을 보정용/평가용으로 분리하여 보정용에서만 곡선을 적합하고, 평가용에서 개선이 확인된 헤드만 채택한다.

#### 판정선은 곡선으로 옮기는 것만으로 보존되지 않는다(2026-08-17 수정)

확률을 보정했으면 판정 임계값도 보정 공간의 값이어야 한다. 처음에는 원본 임계값을 같은 곡선에 통과시켜(`event_threshold()`) 판정선으로 삼았고, 근거는 "보정은 단조 증가 변환이라 순위가 보존되므로 판정이 그대로다"였다. **이 논리는 곡선이 순증가일 때만 성립한다.** 등온 회귀의 결과는 계단 모양이라 평탄 구간을 가지며, 원본 확률이 서로 다른 표본들이 같은 보정값으로 접힌다. 임계값이 그 평탄 구간 안에 떨어지면 구간 전체가 한쪽으로 몰려 판정되어, 실효 임계값이 의도한 위치에서 벗어난다.

한파 헤드 디커플링 직후 실제로 드러났다. 임계값 0.500을 곡선으로 옮긴 0.196으로 판정하자 F1이 **0.4566 → 0.4484**로 떨어졌다 — 디커플링으로 얻은 이득(+0.009)과 같은 크기의 손실이다. 그때까지는 네 헤드 모두 보존되거나 차이가 0.0003 수준이어서 문제가 보이지 않았다.

수정은 임계값을 **판정이 실제로 이뤄지는 공간(보정 후)에서 직접 고르는** 것이다. 고르는 표본과 채점하는 표본을 분리하고, 순이득이 0.01 이상일 때만 재선정값을 채택한다(임계값 선정 규약과 동일). `calibrated_threshold_check.py`로 세 방식을 같은 평가용 표본에서 비교했다.

| 헤드 | ① 원본 공간(이상적) | ② 곡선으로 옮김(이전 방식) | ③ 보정 공간 직접 선정 | 채택 |
|---|---|---|---|---|
| 폭염 | 0.8144 | 0.8144 | 0.8142 | ② 유지(순이득 −0.0002) |
| 한파 | 0.4566 | 0.4484 | **0.4608** | **③ 채택(순이득 +0.0125)** |
| 황사 | 0.1889 | 0.1894 | 0.1909 | ② 유지(순이득 +0.0015) |

한파만 기준을 넘어 재선정값(보정 공간 t=0.224)을 채택했다. 폭염(0.389)·황사(0.084)는 옮긴 값을 그대로 쓴다. 채택된 판정선은 체크포인트에 `threshold_decision`으로 저장되어 서빙이 그대로 읽는다 — 이 키가 없는 구버전 체크포인트는 이전 방식으로 동작한다.

배포 의존성을 늘리지 않기 위해 scikit-learn을 사용하지 않는다. PAVA(pool adjacent violators)를 직접 구현하고 결과를 조회표로 저장하여, 추론 시에는 `numpy.interp`만으로 적용한다.

강수 헤드에는 보정을 적용하지 않는다. 화면에 확률이 아니라 mm로 표시되며, 강수량 = 확률 × 양(amount) 구조에서 양 헤드가 보정 전 확률과 곱해지도록 함께 학습되었기 때문이다. 곡선은 분석 목적으로 체크포인트에 보존하되 서빙 경로에서는 호출하지 않는다.

### 예측 구간 — 분포무관 예측구간(split conformal prediction)(2026-08-18)

화면의 "±"는 검증셋 평균오차일 뿐 이 예측 한 건의 신뢰구간이 아니라는 한계가 있었다(헤드 드롭아웃 검토 당시 지적됨, MC Dropout은 계절 오탐 재발로 기각 — [기각한 시험](#기각한-시험--강수-헤드-부호-표현--헤드-드롭아웃2026-08-17) 참고). `conformal_interval_fit.py`는 **가중치를 전혀 바꾸지 않는 사후 보정**으로 이 문제를 다룬다. 검증셋을 보정용/평가용 절반으로 나누고(확률 보정과 같은 재분할), 보정용에서 부호 있는 잔차(실측−예측)의 (α/2, 1−α/2) 분위수로 구간 폭을 구해 평가용(적합에 전혀 쓰이지 않은 절반)에서 실측 커버리지를 확인한다. 분포를 가정하지 않으므로 표본이 극히 적은 경우에도 커버리지가 깨지지 않고 구간이 넓어지는 형태로만 나타난다.

층화(Mondrian conformal) 축은 헤드마다 다르다. 기온은 관측소별로 층화한다(관측소마다 물리적 기준이 다를 수 있다는 검증 규약과 동일). 강수는 처음에 기온과 같은 방식(관측소별)으로 시도했으나 실패했다 — 검증셋의 93.9%가 무강수라 분위수가 그 다수에 지배되어, 실제 강수(습윤) 표본의 조건부 커버리지가 목표 90%에서 **7%**까지 떨어졌다. head_rain(hurdle)이 이미 겪은 것과 같은 문제("오는가"와 "얼마나"를 뭉뚱그리면 안 된다)라서, 강수는 **예측된 강수확률(rain_prob) 구간**으로 층화한다 — 관측소·시각별 물리적 조건 차이를 반영하면서도 추론 시점에 실제로 쓸 수 있는 값(참값 습윤 여부가 아니라 모델이 낸 확률)만 층화 축으로 쓴다는 게 핵심이다.

| 헤드 | 층화 축 | 층화 없음 커버리지 | 층화 적용 커버리지 | 목표 |
|---|---|---|---|---|
| 기온 | 관측소(12개) | 0.8985 | 0.8994 | 0.90 |
| 강수 | 예측 강수확률 구간(4개) | 0.9018 | 0.9294 | 0.90 |

버킷팅 후 각 층은 목표에 근접했지만, **강수의 습윤 조건부 커버리지는 여전히 60.8%로 90%에 못 미친다.** 이는 정합적 예측의 결함이 아니라 "참 라벨로 조건화한 커버리지는 분포무관 방법으로 보장할 수 없다"는 알려진 한계이며, 예측확률이 낮았는데 실제로 비가 온 사건(강수 헤드가 놓친 사건)은 애초에 좁은 구간을 받으므로 못 잡는다. 채택 기준(층화 그룹 평균 커버리지가 목표−0.02 이상)에는 이 값을 넣지 않았다 — 채점 불가능한 기준을 채택 조건으로 쓰면 실패를 숨기는 셈이기 때문이며, 대신 실측값을 그대로 남긴다.

강수의 층화 커버리지가 목표를 웃도는(0.9294) 것은 과대 포함이다. 무강수 표본이 94%라 해당 층의 구간이 [0, 0]으로 수축하는데, 실측도 0이라 전부 포함되기 때문이다. 정합적 예측의 보장은 "1−α **이상**"이므로 이는 보장 위반이 아니라 보수적인 쪽이며, 대신 그 층의 구간은 정보량이 거의 없다.

**초판(2026-08-18)의 수치는 두 가지 산출 오류를 포함하고 있어 정정한다(2026-08-19).**

첫째, 구간 상한에 하한과 같은 clip이 걸려 있지 않았다. 무강수 층에서는 잔차 상한 분위수가 음수라(버킷 0에서 −0.00000, 버킷 1에서 −0.00005) `상한 = 예측 + 분위수`가 0보다 작아지는데, 하한만 0으로 clip하면 `[0, 음수]`라는 **뒤집힌 구간**이 만들어져 무조건 미포함으로 집계된다. 평가 표본의 **2.99%**가 실제로 이 상태였고, 이를 고치자 강수 커버리지가 0.8996에서 0.9294로 바뀌었다 — 즉 초판의 0.8996은 뒤집힌 구간을 미포함으로 세어 나온 값이었다.

둘째, 잔차 분위수의 유한표본 순위 계산에서 아래쪽에도 `ceil`을 써 목표를 **구조적으로** 밑돌았다. 연속 잔차에서 실현 커버리지는 정확히 `(hi_rank − lo_rank)/(n+1)`인데, 양쪽 모두 올림하면 아래쪽 순서통계량을 하나 더 잘라낸다 — n=200에서 0.8955, n=1,000에서 0.8991로 잡음이 아니라 결정적 미달이다. 이 상태로는 "커버리지가 목표 이상"이라는 채택 기준이 원리적으로 충족될 수 없어, 게이트가 허용오차 아래에 숨는 형태로 무력화된다. 아래쪽을 `floor`로 고쳤다(대표본에서는 영향이 0.001 미만이라 위 표의 수치는 바뀌지 않았고, 표본이 작은 관측소별 층에서 의미가 있다).

결과는 체크포인트의 `conformal_interval` 키에 저장했다(백업: `numerical_trichef_before_conformal.pt`, 정정 전 상태는 `numerical_trichef_before_conformal_fix_20260819.pt`). **현재 화면(Streamlit)에는 아직 연결하지 않았다** — 계산·검증까지만 마쳤고, 표시 UI 연결은 남은 작업이다.

### 정정 — 한파 헤드 중첩 극한사건 전이학습 실험의 "기각" 결론은 무효였다(2026-08-18)

2026-08-18에 이 절에 "커리큘럼 사전학습을 거쳐도 이득이 없다"고 기각 기록을 남겼으나, **실험 자체가 의도대로 실행되지 않았다는 것을 이후에 발견해 정정한다.**

원래 절차는 `coldwave_nested_pretrain.py`로 약한 라벨 커리큘럼 사전학습 체크포인트를 만든 뒤, 그 경로를 `CHECKPOINT_PATH` 환경변수로 넘겨 `head_decouple_finetune.py --heads coldwave`가 그 체크포인트를 기반으로 공식 라벨 미세조정을 잇는 것이었다. 그런데 `predict.py`의 `CHECKPOINT`가 하드코딩 리터럴이라 환경변수를 전혀 읽지 않았고, `head_decouple_finetune.py`는 위치 인자로 경로를 받지 않아 `from predict import CHECKPOINT`의 기본값에만 의존한다 — 그래서 `CHECKPOINT_PATH`가 조용히 무시되고, "1회차"·"2회차" 두 미세조정 실행 모두 사전학습을 거치지 않은 **프로덕션 체크포인트**를 그대로 불러와 일반 디커플링을 두 번 돌린 셈이 됐다.

30에폭 평균 F1이 두 실행에서 소수점 넷째 자리까지 일치(0.4580)했던 것도 이걸로 정확히 설명된다 — 서로 다른 두 조건(사전학습 유무)을 비교한 게 아니라 **같은 조건을 두 번** 돌린 것이었기 때문이다. 즉 "중첩 전이학습이 이득 없음"이라는 결론 자체가 성립하지 않는다.

`predict.py`의 `CHECKPOINT`를 `train.py`와 같은 `os.getenv("CHECKPOINT_PATH", ...)` 패턴으로 고쳐 원인을 제거했다. 이 버그는 위치 인자로 체크포인트 경로를 받지 않고 `predict.CHECKPOINT` 기본값에만 의존하는 다른 스크립트에도 잠재했을 수 있다 — 여러 체크포인트를 오가며 쓸 때는 로그에 찍히는 "기반 체크포인트" 줄과 대상 파일의 크기·수정시각을 대조해 실제로 의도한 파일이 로드됐는지 확인할 것.

**사전학습 스크립트 자체에도 별개의 결함이 두 개 더 있었다(2026-08-19 코드 점검에서 발견).**

첫째, 헤드 재초기화(`reinit_head`)가 스테이지 반복문 **안**에 있었다. 그래서 p20 단계가 학습한 가중치를 p10 단계가 지우고 무작위 초기값에서 다시 시작했고, p5도 마찬가지였다 — 결과가 "p5 한 단계만 돌린 것"과 비트 단위로 같아진다. **중첩 전이학습의 핵심인 warm start가 한 번도 일어나지 않았다.** 단계별 참고 F1이 0.239 → 0.348 → 0.413으로 올라간 것도 학습이 누적된 결과가 아니라, 약한 라벨의 임계값이 공식 한파 정의에 가까워지면서 같은 정답에 근접한 효과였다. 재초기화를 커리큘럼 시작 전 1회로 옮겼다.

둘째, `reset_parameters()`가 마지막 층의 편향까지 되돌리면서 `_binary_head`가 심어둔 사전확률 로짓을 지웠다. 희소 사건에서 "대부분 음성"을 학습 시작 시점부터 반영하려고 일부러 넣은 값인데, 이게 사라지면 헤드가 p≈0.5에서 출발한다. 이 스크립트의 학습 루프에는 `pos_weight`도 없어 보정되지 않는다. 재초기화 직후 학습 표본에서 실측한 사전확률로 편향을 다시 심도록 고쳤다.

### 재시도 결과 — 효과는 있으나 30에폭 끝까지 남지 않는다(2026-08-19)

위 두 결함(재초기화 위치, 사전확률 편향 소실)을 고친 뒤 다시 돌렸다. 이번엔 스테이지 간 `head_coldwave` 가중치 노름을 직접 로그로 남겨 warm start가 실제로 일어나는지 확인했다 — 초기화 직후 3.56~3.57에서 스테이지를 거치며 18.4→19.6→20.6(1회차), 18.1→19.4→20.4(2회차)로 매 단계 이전 값에서 이어졌다. 코드만 읽고 판단했던 지난번과 달리 이번엔 실행 결과로 직접 확인했다.

미세조정(공식 라벨, 30에폭)을 독립적으로 두 번 돌렸다.

| 실행 | 30에폭 평균 F1 | 기준선(0.4580) 대비 | 최선 에폭(참고) |
|---|---|---|---|
| 1회차 | 0.4662 | **+0.0082** | 에폭 3 — 0.496 |
| 2회차 | 0.4669 | **+0.0089** | 에폭 3 — 0.500 |

사전 등록한 채택 기준(두 실행 모두 +0.005 이상, 같은 방향)을 충족한다 — 이번엔 노이즈가 아니라 실제 효과다. 다만 그 효과의 정체를 규명해야 한다. 두 실행 모두 같은 모양의 곡선을 보인다 — 에폭 2~4에서 F1이 0.49~0.50까지 치솟았다가 에폭 15 이후 0.457~0.461로 가라앉는다. **마지막 10에폭 평균은 1회차 0.4590, 2회차 0.4589로 기준선과 사실상 같다(+0.001, 노이즈 범위).**

즉 30에폭 평균이 기준을 넘은 것은 초반 몇 에폭의 큰 이득이 평균을 끌어올렸기 때문이지, 30에폭 끝까지 학습한 최종 모델이 더 나은 것이 아니다. 공식 라벨로 계속 미세조정할수록 커리큘럼이 준 이점이 점차 덮어써지는 것으로 보인다(전이학습 문헌의 catastrophic forgetting과 일치).

**"에폭 3이 최선"이라고 바로 채택하지 않는다.** 같은 검증 곡선을 보고 정지 시점을 고르면 과거 "최선 에폭 고르기" 함정(순이득 +0.0054가 노이즈였던 사례, 위 문단 참고)과 원리가 같다 — 순환 논리다. 다만 이번엔 그 정지 시점의 모양(에폭 2~4 근방에서 정점, 이후 단조 하강)이 **독립된 두 실행에서 재현**된다는 차이가 있다. 재현된 형태를 근거로 조기 종료를 실제로 채택하려면, 이 곡선을 만드는 데 쓰지 않은 별도 표본(세 번째 독립 실행, 또는 별도 조기종료 판정용 분할)에서 미리 정한 정지 에폭이 유지되는지 확인해야 한다 — 지금까지의 두 실행은 서로를 재현했을 뿐, 정지 시점 선택 자체를 검증한 것은 아니다.

### 정지 시점 검증 및 승격(2026-08-19)

위에서 지적한 순환 논리를 없애기 위해, `head_decouple_finetune.py`에 `--calib-eval-split` 옵션을 추가했다. 검증셋을 보정용/평가용 절반으로 나누고(확률 보정과 같은 `CALIB_SEED=1234` 재사용), **정지 에폭은 보정용 곡선만으로 고르고 그 에폭의 성능은 한 번도 안 본 평가용에서만 잰다** — 확률 임계값 선정(CLAUDE.md 2절)과 같은 원칙을 정지 에폭 선택에 적용한 것이다.

기존 사전학습 체크포인트(1·2회차)를 재사용해 이 방식으로 두 번 돌렸다.

| 실행 | 보정용 곡선이 고른 정지 에폭 | 그 에폭의 평가용 F1 | 기준선(0.4576) 대비 |
|---|---|---|---|
| 1회차 | 3 (보정용 F1 0.494) | 0.501 | +0.0434 |
| 2회차 | 3 (보정용 F1 0.494) | 0.503 | +0.0454 |

두 실행에서 **정지 에폭이 정확히 일치**했고(보정용 F1도 소수점 셋째 자리까지 동일), 평가용 F1도 0.501/0.503으로 사실상 같다. 보정용 곡선과 평가용 곡선이 에폭 내내 거의 평행하게 움직였다(차이가 +0.007~+0.023 범위에서 유지) — 정지 시점이 이 특정 곡선의 잡음이 아니라 실제 신호라는 근거다. 순환 논리 없이 확인된, 이 저장소에서 가장 큰 폭의 검증된 개선이다.

흥미롭게도 기존 "최선 에폭" 저장 로직(전체 검증셋 기준, 보정용/평가용 분할과 무관하게 원래 있던 로직)도 두 실행 모두 독립적으로 에폭 3을 골랐다 — 별도로 저장할 필요 없이 이미 저장된 체크포인트가 그대로 검증 대상이었다.

**승격 게이트 3종을 전부 통과했다.**

| 게이트 | 1회차 | 2회차 |
|---|---|---|
| 계절 오탐 | PASS(0.014%) | PASS(0.013%) |
| 단조성(한파, corr) | PASS(−0.61) | PASS(−0.67) |
| 단조성(폭염, corr) | PASS(+0.71) | PASS(+0.68) |
| 관측소 사각지대 | PASS(폭염·한파), WARN(황사 — 기존과 동일한 구조적 문제) | 동일 |
| 회귀 성능(한파 F1) | 0.4576 → 0.4977 | 0.4576 → 0.4987 |

과거 헤드 드롭아웃 실험이 F1은 최고였는데 계절 오탐 게이트에서 FAIL했던 전례(위 "기각한 시험" 참고)와 달리, 이번엔 계절 오탐이 오히려 배포본보다도 낮다.

두 후보가 통계적으로 사실상 같아, 모든 지표에서 근소하게 앞선 2회차(`numerical_trichef_coldwave_calibeval_run2.pt`)를 `promote_checkpoint.py --promote`로 승격했다. 트렁크·기온·강수·폭염·황사 헤드는 동결 상태로 학습했으므로 가중치가 그대로이며, 한파 헤드만 바뀌었다. 승격 직후 확률 보정을 4개 헤드 모두 재적합했고(한파 판정선 0.229), 신뢰도 곡선·관측소별 플롯도 새 모델 기준으로 재생성했다. 승격 전 상태는 `numerical_trichef_before_20260819_004345.pt`로 백업했다.

`+12h` 부체크포인트도 같은 커리큘럼으로 승격했다(한파 F1 0.453 → 0.509) — 경위는 위 [+12시간 2차 산출값](#12h-secondary) 절 참고.

**관측소별 예외는 전주 한파 하나가 새로 채택됐다.** `calibration_plot_diagnose.py`가 그린 관측소별 정밀도×재현율 산점도에서 전주 한파 정밀도가 18.1%로, 나머지 관측소(35~58%, 신뢰구간이 서로 겹치지 않음)와 뚜렷이 구분되는 이상치였다. `station_threshold_check.py --station=146 --event=coldwave`로 보정용/평가용 분리 검증한 결과:

| 항목 | 값 |
|---|---|
| 판정 가능 표본 | 5,304개(양성 192개) |
| 보정용에서 고른 t | 0.33 |
| 평가용 F1(t=0.33) | 0.1905 |
| 평가용 F1(전역 t=0.50) | 0.1216 |
| 순이득 | **+0.0689** |

채택 기준(0.01)을 크게 넘어 `predict.py`의 `STATION_EVENT_THRESH_OVERRIDES`에 `("146", "coldwave"): 0.33`을 추가했다. 이 값은 원본(보정 전) 확률 공간의 임계값이다 — `event_threshold()`가 관측소별 예외를 `calibrate_prob()`에 통과시켜 보정 공간으로 옮긴 뒤 비교하므로, 검증에 쓴 것과 같은 공간(raw)에서 고른 값을 그대로 넣는 것이 맞다(12절 규약).

부산 폭염 예외(과거 0.33)는 이번에도 재검증해 순이득 −0.0033으로 다시 기각됐다 — 2026-08-17 결론과 동일하다.

절대 F1(0.19)은 여전히 낮다 — 전주 자체가 표본 부족(사건 단위로 세면 더 적을 수 있음)과 구조적 판별 신호 부족을 겪고 있을 가능성이 높다. 이 예외는 "낮은 성능을 고친다"가 아니라 "전역 임계값보다 그 관측소 표본에서 실측으로 더 나은 값을 쓴다"는 좁은 의미로만 유효하다.

<a id="null-calibration-overrides"></a>

**널 캘리브레이션으로 5건이 추가 채택됐다(2026-08-31).** 관측소별 예외를 균일 격자 그리드서치가 아니라 다른 탐색 공간에서도 찾을 수 있는지 시험했다 — Risk_Prediction 프로젝트의 널 캘리브레이션(무사건 구간 확률의 μ+z·σ를 임계값 후보로 역산)을 `null_calibration_check.py`로 이식해, 같은 보정용/평가용 분리(순이득 0.01 게이트)로 12개 관측소 × 3개 헤드(폭염·한파·황사) 전부를 훑었다.

이 방법은 **관측소별 무사건 분포(μ_null, σ_null)로 임계값을 재매개변수화**해 균일 격자 대신 그 관측소에 맞춘 성긴 후보만 탐색한다. 다만 z 자체는 보정용 절반의 F1로 고르므로 **목적함수는 기존 그리드서치와 동일하다**(2026-08-31 정정 — 최초 서술은 "F1을 직접 보지 않는 방법"이라 했으나 코드와 어긋났다. 따라서 "두 방법의 F1이 일치했으므로 방법이 검증됐다"는 추론도 성립하지 않는다. 같은 표본에서 같은 목적함수를 최대화했으니 일치가 당연하다).

**후보 8건 중 3건은 채택하지 않았다.** 여기서 잰 순이득은 원본(raw) 확률 공간의 값인데 서빙은 보정 후 공간에서 판정하므로, 임계값이 등온 회귀의 평탄 구간에 떨어지면 판정이 보존되지 않는다([확률 보정 절](#prob-calibration), 실제 F1 0.4566→0.4484 사고 이력). 곡선에 대조한 결과 **인천 폭염(raw 0.6565)과 수원 한파(raw 0.6000)** 가 τ±0.01 구간에서 보정폭 0.0인 완전 평탄 구간에 떨어져 제외했다 — raw 공간의 이득이 서빙에서 재현된다는 근거가 없기 때문이다.

| 관측소 | 이벤트 | τ(원본 공간) | 그 관측소 F1 | 보정폭(τ±0.01) |
|---|---|---|---|---|
| 청주 | 폭염 | 0.7142 | 0.7842 → 0.7995 | 4.7e-02 |
| 수원 | 폭염 | 0.6781 | 0.8016 → 0.8162 | 4.5e-03 |
| 강릉 | 한파 | 0.4167 | 0.3947 → 0.4000 | 2.7e-02 |
| 서울 | 한파 | 0.6129 | 0.5451 → 0.5542 | 7.0e-03 |
| 인천 | 한파 | 0.5269 | 0.4444 → 0.4494 | 5.9e-02 |
| ~~인천~~ | ~~폭염~~ | ~~0.6565~~ | — | **0.0 — 평탄, 기각** |
| ~~수원~~ | ~~한파~~ | ~~0.6000~~ | — | **0.0 — 평탄, 기각** |
| ~~광주~~ | ~~한파~~ | ~~0.1749~~ | ~~0.0000 → 0.0980~~ | 1.3e-02 — **합산 악화, 기각** |

**광주 한파는 평탄 구간 검사를 통과했는데도 기각했다 — F1이 부분집합에서 합산으로 분해되지 않기 때문이다.** 광주 자체 표본에서는 F1이 0.0000에서 0.0980으로 크게 올랐으나, 임계값 0.1749가 너무 낮아 그 관측소에서 오탐이 쏟아지고 그것이 합산 정밀도를 끌어내려 **합산 한파 F1이 0.5001 → 0.4859로 떨어졌다**(실측). 양성 96건을 얻으려다 3,864건 전체의 지표를 깎는 셈이다. 관측소별 순이득이 양수여도 합산이 양수라는 보장은 없으므로, 앞으로 관측소별 예외는 그 관측소 순이득과 **합산 지표 비회귀**를 함께 확인한다.

채택한 5건의 합산 효과는 폭염 0.8139 → **0.8165**(+0.0026), 한파 0.5001 → **0.5004**(+0.0003), 황사 변화 없음이다.

전주 한파(146)는 두 방법이 서로 다른 값(그리드서치 0.33 vs 널 캘리브레이션 0.2032)을 제시했는데, 기존 0.33이 이미 프로덕션에서 검증된 값이라 대체하지 않고 유지했다. 황사는 통과한 관측소가 없었다(기존에도 약한 헤드로 진단됨).

### 지표 분리 측정과 오차 분해(2026-08-17)

지금까지 세 지표는 서로 다른 스크립트에서, 서로 다른 분할로 나왔다. 회귀 MAE는 `train.py`, 분류 F1은 `patch_extreme_metrics.py`, 보정 오차는 `probability_calibration_check.py`가 각각 냈고 임계값 검증은 또 검증셋을 절반으로 쪼갠다. 그래서 "F1은 올랐는데 신뢰도는 어떻게 됐나"를 물으면 표본이 다른 숫자를 비교하게 된다. `eval_cache.py`가 검증셋 추론을 한 번만 수행해 캐시로 남기고, `metrics_report.py`가 그 **동일 표본 하나**에서 세 축을 모두 산출한다.

|---|---|
| 정확도(accuracy) | 기온 MAE 1.2966°C(기준선 대비 −61.2%) · 강수 MAE 0.1665mm(원본, +9.9% 미달) / 0.1573mm(서빙 후처리 후, +3.8% 미달) · 적중률 기온 ±1.5°C 이내 67.0% · 강수 발생 여부 일치 94.0% |

#### 강수는 어디서 지고 있는가 — 무강수 구간이 전부다

`error_breakdown.py`로 전체 MAE를 구간별로 분해했다. 전체 MAE는 구간별 MAE의 표본 수 가중평균이므로 기여도를 `n_i/N × MAE_i`로 정확히 나눌 수 있고, 기준선도 같은 방식으로 분해하면 두 기여도의 차이가 곧 그 구간이 만든 격차다(합이 전체 격차와 일치함을 검산으로 확인했다).

![오차 분해](docs/images/error_breakdown.png)

| 강수 강도 | 표본 | 비중 | 모델 MAE | 기준선 | 격차 기여 | 격차 점유 |
|---|---|---|---|---|---|---|
| **무강수** | 259,101 | 93.8% | 0.0322 | 0.0000 | **+0.0302** | **201.2%** |
| 0.1~1mm | 8,361 | 3.0% | 0.4860 | 0.3731 | +0.0034 | 22.7% |
| 1~5mm | 6,374 | 2.3% | 1.9010 | 2.2669 | −0.0085 | −56.2% |
| 5~20mm | 2,081 | 0.8% | 7.6315 | 8.8578 | −0.0092 | −61.5% |
| 20mm 이상 | 199 | 0.1% | 27.9780 | 29.2884 | −0.0009 | −6.3% |

**실제로 비가 오는 구간에서는 모델이 기준선을 이긴다.** 1mm 이상 전 구간에서 격차 기여가 음수다. 지는 이유는 오직 하나 — 표본의 93.8%를 차지하는 무강수 구간에서 softplus가 정확한 0을 내지 못해 표본마다 평균 0.032mm의 오차를 깔기 때문이다. 이 구간 하나가 전체 격차의 201%를 만들고, 강수 구간의 이득이 그중 101%를 상쇄한다.

> **[2026-08-31 갱신] 이 분해는 강수 확률 게이팅 배포(2026-08-29) 이전 측정이며, 지금은 구조가 바뀌었다.** 게이팅이 무강수 구간 문제를 대부분 해소해, 현재 배포 경로의 오차 출처는 무강수 12.3% / 강수 **87.7%** 다. 즉 남은 격차를 지배하는 것은 더 이상 "0을 못 내는 것"이 아니라 **강수 구간의 강도 예측**이다. 상세는 [강수 축 상한 분석](#precip-ceiling)을 참조한다.

이 진단은 개선 방향을 바꾼다. 강수 표현력을 키우는 구조 변경(트렁크 분리 등)은 **이미 이기고 있는 구간**을 겨냥하는 셈이다. 처방은 무강수 구간의 미세 출력을 0으로 만드는 쪽에 있다.

> 위 표(강수 강도별 분해)는 2026-08-17에 잰 원본(후처리 전) 모델 출력 기준이며, 모델 가중치가 바뀌지 않아 지금도 그대로 유효하다. 처방 자체는 2026-08-29에 [확률 공간 게이팅](#precip-prob-gate)으로 실현됐다 — 아래 매그니튜드 임계값 실험과 다른 결과를 낸다.

#### 후처리 임계값을 올리면 이기지만, 채택하지 않는다

당시(2026-08-17) 후처리(0.2mm 미만 → 0, 지금은 [확률 게이팅](#precip-prob-gate)으로 대체됨)를 적용하면 격차가 **+9.9% → +6.0%**로 줄어들었다. 문서와 대시보드가 인용하는 −9.9%는 후처리 **전** 모델 출력 기준이며, 당시 화면에 실제로 나가던 값은 −6.0% 수준이었다. 두 값을 구분해 적는다.

임계값을 보정용 절반에서 재산출하면 t=2.95mm가 뽑히고 평가용 MAE가 0.1506mm로 **기준선을 처음으로 넘는다(−0.2%)**. 그러나 채택하지 않았다.

| 설정 | 평가용 MAE | 기준선 대비 | 강수 발생 F1 |
|---|---|---|---|
| 후처리 없음(t=0) | 0.1659 | +9.9% | 0.448 |
| 현행 t=0.20 | 0.1600 | +5.9% | **0.430** |
| 재산출 t=2.95 | **0.1506** | **−0.2%** | 0.103 |

#### 결정 — 강수의 주 지표를 바꾼다

위 두 결과가 같은 것을 가리킨다. 표본의 93.8%가 무강수인 분포에서 **MAE 단독 최적화는 언제나 "거의 항상 0"이라는 퇴화 해로 끌린다.** 강수에서 MAE가 실용 가치를 대변하지 못한다는 판단은 이전부터 문서에 있었으나, 이제 수치적 근거가 생겼으므로 지표 체계를 그에 맞춘다.

| | 지표 | 값 |
|---|---|---|
| **주 지표** | 강수 발생 판정 F1 | **0.463**(정밀도 51.6% · 재현율 41.9%, 2026-08-29 [확률 게이팅](#precip-prob-gate) 적용 후) |
| **주 지표** | 강수 구간 조건부 MAE | **2.2396mm** vs 기준선 2.4584mm — **−8.9% 개선** |
| 보조 | 무강수 구간 MAE | 0.0206mm vs 기준선 0.0000mm |
| 병기 | 전체 MAE | 0.1665mm(원본, +9.9%) / 후처리 후 0.1573mm(+3.8%) |

전체 MAE는 정직성 차원에서 계속 표시하되 **판단 근거에서는 내린다.** "비가 오는 상황에서 얼마나 잘 맞히는가"는 −8.9% 개선이고, "비가 오지 않는 상황에서 0을 얼마나 잘 내는가"는 아직 못 이긴다 — 두 질문을 하나의 MAE로 통합하면 어느 쪽도 알 수 없다.

t=2.95는 "2.95mm 미만은 전부 0"이라는 뜻이므로, 실질적으로 **기준선을 모사하여** MAE를 이긴다. 그 대가로 강수 발생 판정 F1이 0.430에서 0.103으로 무너진다. 표본의 93.8%가 무강수인 분포에서 MAE 단독 최적화는 언제나 이 방향으로 끌리며, 이는 강수에서 MAE가 실용 가치를 대변하지 못한다는 기존 판단([정직한 한계 4](#4-1시간-예보는-무의미했으며-강수는-여전히-기준선에-미달한다))을 수치로 재확인한 것이다. `error_breakdown.py`는 이 함정을 자동으로 판정하도록 MAE 이득과 발생 F1 손실을 함께 출력한다.

<a id="precip-prob-gate"></a>

#### 강수 확률 게이팅 — F1과 MAE가 함께 개선되는 축을 찾았다(2026-08-29)

위 실험은 모두 `rain_prob × amount` 곱 자체를 매그니튜드(mm) 임계값으로 자르는 방식이었다. 이 곱은 강수 발생 판정 F1을 계산하는 값과 동일하므로(0.1mm로 이진화), 매그니튜드 임계값을 올려 MAE를 이기면 F1도 같은 knob을 타고 무너진다 — t=2.95의 결과가 그 증거다.

`rain_prob` **자체**에 별도 임계값(τ)을 걸면(매그니튜드 크기와 무관하게 분류기 확신도만으로 0 여부를 정하면) 이 결합이 끊긴다. `precip_prob_gate_sweep.py`(재학습 없이 `cache/eval_cache.npz`만 재사용)로 검증셋 평가용 절반(채점에 쓰지 않은 표본)에서 확인한 결과, τ 0.80~0.91 구간 **전체에서 F1과 MAE가 동시에 개선**됐다.

| τ | F1 | MAE 기준선 대비 | MAE_dry |
|---|---|---|---|
| 현행(구, mm clip 0.2) | 0.4296 | +5.9% | 0.0238 |
| 0.80 | 0.4679 | +5.1% | 0.0230 |
| 0.85(+6h 채택값) | 0.4637 | +3.8% | 0.0203 |
| 0.91 | 0.4396 | +1.6% | 0.0154 |
| 0.93 | 0.4103(F1이 기준선 아래로 하락) | +0.9% | 0.0132 |

τ≈0.93부터 F1이 기준선 아래로 꺾이는 절벽이 있어, 절벽에서 떨어진 τ=0.85를 채택했다(자동 선정 규칙 — "F1이 현행 이상인 후보 중 MAE_dry 최소"를 그대로 따르면 절벽 바로 앞인 0.91이 뽑히지만, 재현성 여유를 위해 사람이 더 보수적인 값을 골랐다). `error_breakdown.py --served`의 독립 재산출도 τ=0.84를 골라 사실상 같은 값으로 수렴했다(그리드 해상도 차이).

**+6h와 +12h 체크포인트에 같은 τ를 쓰면 안 된다.** rain_prob 분포가 리드타임마다 달라(+12h는 90백분위가 0.75에 그침) 0.85를 그대로 쓰면 +12h의 F1이 오히려 0.3560→0.3497로 떨어졌다(실측). 같은 절차로 +12h 전용 값을 독립적으로 골랐다 — τ=0.75, 평가용 F1 0.3591→0.3805, MAE 기준선 대비 +17.7%→+17.2%. 두 값은 `predict.py`의 `PRECIP_PROB_GATE_BY_LEAD = {6: 0.85, 12: 0.75}`에 저장되어 체크포인트의 `lead_hours`로 자동 선택된다.

**숨기지 않는 대가.** τ가 오를수록 정밀도는 오르고 재현율은 떨어진다(+6h 기준 45.0%/41.1% → τ=0.85에서 51.6%/41.9%). F1은 개선되지만 "오탐은 줄고 약한 비 누락은 늘어난다"는 성격 변화가 실제로 생긴다.

이 변경은 재학습이 아니라 추론 후처리(`predict.py`의 무강수 판정 방식)만 바꾼 것이라 체크포인트는 그대로다. `metrics_report.py`·`error_breakdown.py`가 새 게이팅 방식을 반영하도록 함께 갱신했다.

#### 후속 시도 — Gamma NLL 재도전(중앙값 점추정), 보류(2026-08-29)

2026-08-18 Gamma NLL 실험이 −147.5%로 실패한 원인을 재검토했다. Gamma 분포 모델링 자체가 아니라 **최종 점추정 방식**이 문제였다 — `rain_prob × E[amount|wet]`(조건부 평균)은 0에 확률질량이 몰린 혼합분포에서 절대오차(MAE)를 최소화하는 점추정이 아니다. MAE 최적 점추정은 **중앙값**이며, 닫힌 형태를 유도해 몬테카를로로 검증했다(`gamma_median_test.py`, 최대 상대오차 0.2%). `forward()`의 반환 shape은 바뀌지 않는다 — Gamma NLL 분기는 이미 μ·α를 별도 속성으로 저장하고 손실도 그 속성에서 직접 계산하므로, 점추정 한 줄만 바뀐다(학습 루프는 저렴한 곱셈 값을 쓰고, 추론·검증에서만 올바른 중앙값을 쓰도록 분리해 학습 속도 저하도 피했다 — `pipeline_model.hurdle_gamma_median()`).

`PRECIP_GAMMA_NLL=1`로 별도 경로(`numerical_trichef_gamma_median_20260829.pt`)에 재학습한 결과, **단순 승패가 아니라 새로운 트레이드오프**가 나왔다.

| | production(현재 배포) | Gamma NLL + 중앙값 |
|---|---|---|
| F1 상한(τ 스윕 전 구간 중 최댓값) | ~0.466 | **0.510**(τ=0.85, 평가용 재확인 0.5096) |
| production과 비슷한 MAE(+3.8~5.4%)로 맞춘 지점의 F1 | 0.4637(τ=0.85) | 0.4685(τ=0.91) — 사실상 동급 |

같은 MAE 수준에서는 두 접근이 사실상 동급이고, 새 접근의 실질적 이득은 "MAE를 더 희생하면 production이 도달 못하는 F1(0.51)까지 밀어붙일 수 있다"는 새 선택지다. 보정용/평가용 절반에서 F1이 0.5161/0.5096으로 거의 일치해 재현성도 확인했다.

**승격하지 않는다 — 규모가 다르다.** 이번 학습은 트렁크를 포함해 전체를 처음부터 다시 돌린 것이라, 그동안 개별적으로 쌓아온 다른 헤드의 미세조정이 전부 빠졌다. 한파 F1이 0.499(중첩 전이학습 승격값)에서 0.438로, 황사가 0.191에서 0.166으로 후퇴했다(폭염은 0.814→0.804로 근소). 강수만 놓고 보면 유망하지만, 이 체크포인트를 그대로 배포하면 한파가 퇴보한다. 승격하려면 이 강수 메커니즘 위에 한파 중첩 전이학습·임계값 재선정·계절 오탐/단조성 게이트를 전부 다시 쌓아야 한다 — 오늘 착수 범위를 넘는 별도 과제로 남긴다.

#### 다음 단계 검토 — 관측 확장의 정보이론적 근거(2026-08-29)

Gamma NLL 재도전으로도 강수 발생 판정 F1은 0.51 부근에서 정체됐다. 다음 단계로 apihub의 추가 관측(AWS·레이더·낙뢰·위성·해양부이 등)을 검토하되, "조밀하게 깔면 좋아질 것"이라는 추측이 아니라 **기존 12개 관측소 자료에서 측정 가능한 것부터 재서** 그 결과로 우선순위를 정했다(`data_expansion_analysis.py`, `data_expansion_probe.py`). API허브 카탈로그 자체도 별도로 조사했다(로그인 없이 열람 가능한 `apiList.do?seqApi=N` 페이지들).

**측정 1 — 너깃(nugget) 보정 변동도.** 관측소 66개 쌍의 거리별 상관을 `r(d) = c₀·exp(−d/L)`로 적합했다. `c₀`는 거리 0으로 수렴할 때의 상관(공간 일관 성분)이고, `1−c₀`가 최소 관측 간격(30km) 아래에 숨은 미해상 분산 — 즉 조밀 관측이 새로 볼 수 있는 몫의 상한이다.

| 변수 | c₀ | 너깃(1−c₀) | 감쇠 길이 L | R² |
|---|---|---|---|---|
| 기온(대조군) | 0.992 | 0.8% | 8,142km | 0.59 |
| 강수 발생 | 0.732 | **26.8%** | 276km | 0.94 |
| 강수량 | 0.394 | **60.6%** | 205km | 0.81 |

기온은 공간적으로 거의 완전히 일관돼(너깃 0.8%) 12개 관측소로 충분하다 — 기온 MAE가 −61.2%로 좋은 구조적 이유다. 강수는 분산의 26.8~60.6%가 관측망 해상도 밖에 있다.

**측정 2 — 이류(advection) 지연.** 관측소 순서쌍의 교차상관을 시차 0~12시간으로 훑어 최대가 되는 시차를 찾았다. 이류가 실제로 잡힌 39개 쌍(전체 132쌍 중)의 함축 이동속도는 중앙값 67km/h(사분위 55~92)였고, 방향 비대칭과 동향(east-ward) 성분의 상관은 `r = +0.934`로 편서풍 이류가 뚜렷했다.

**+6시간 뒤 도달할 강수계는 지금 약 404km 상류에 있다는 뜻이다. 한반도 동서 폭은 약 300km다.** 서풍 계열에서 그 지점은 서해 위이며, 육상 관측소를 아무리 조밀하게 깔아도 물리적으로 관측할 수 없다.

**측정 3 — 특징 절제(feature ablation).** `HistGradientBoostingClassifier`에 특징군을 단계적으로 추가해 AUC 증분을 쟀다(날짜 단위 그룹 분할, 표본 136만 개 — 검증 규약과 동일).

| 특징군 | AUC | ΔAUC | 최대 F1 |
|---|---|---|---|
| 국지 현재 | 0.8571 | — | 0.4601 |
| + 국지 경향(Im축이 가진 것) | 0.8915 | +0.0343 | 0.4843 |
| + 이웃 현재(Re축이 가진 것) | 0.9137 | +0.0222 | 0.5172 |
| + 이웃 경향(현재 어느 축도 갖지 않은 정보) | 0.9147 | **+0.0010** | 0.5179 |

마지막 단계(이웃의 시간 변화, 즉 이류 방향 정보)의 증분이 사실상 0이다. `data_expansion_analysis.py`의 조건부 상호정보량 측정도 같은 결론을 냈다 — 이웃 7~8곳에서 정보가 포화하고(11번째 이웃의 한계 증분 0.5%), 이웃의 현재 강수만으로 만든 예측 상한(oracle) F1은 0.337로 국지 지속성 기준선(0.444)보다도 낮았다.

**결론 — 병목은 관측망을 잘못 쓰는 것이 아니라, 필요한 정보가 물리적으로 관측망 밖(서해)에 있는 것이다.** 세 측정이 모두 같은 곳을 가리킨다. 기존 12개 관측소에서 짜낼 수 있는 공간·시공간 정보는 사실상 소진됐고(정보 상한 F1 ≈ 0.51~0.52, Gamma NLL 실험이 이미 0.510에 도달), 개선하려면 관측을 촘촘히 하는 것(AWS)이 아니라 **서쪽으로 멀리** 봐야 한다.

이 결론에 따라 apihub 후보의 우선순위를 다시 정한다.

<a id="split-algorithm-change"></a>

#### 분할 알고리즘 교체가 만든 제약 (2026-08-31)

위 1번을 고치면서 group 분할이 `torch.randperm(고유 날짜 수)`에서 날짜 문자열 해시 배정으로 바뀌었다. 그 결과 **구 분할로 학습된 체크포인트(현행 배포본 포함)는 현재 코드로 검증셋이 재현되지 않는다.**

| 기준선 | 배포본 저장값 | 현행 코드 재구성값 |
|---|---|---|
| 기온 퍼시스턴스 MAE | 3.3452 | 3.3057 |
| 강수 상시 0 MAE | 0.1515 | 0.1478 |

**처음에는 이것이 되돌릴 수 없는 손실이라고 판단했다 — 틀렸다.** 구 알고리즘(`torch.randperm`)은 (날짜 집합, SEED, VAL_RATIO)에 대해 결정적이므로 그대로 재구성할 수 있다. 체크포인트에 `split_algo`를 기록하고 복원 시 그 값을 따르도록 고쳤다(키가 없는 구버전 체크포인트는 `randperm`으로 읽는다 — CLAUDE.md 1절 7항의 구버전 호환 원칙을 분할 알고리즘에 적용한 것이다). 배포 체크포인트의 저장 기준선을 소수점 6자리까지 재현함을 확인했다.

| 기준선 | 저장값 | 구 알고리즘 재구성 |
|---|---|---|
| 기온 퍼시스턴스 MAE | 3.345163 | **3.345163** |
| 강수 상시 0 MAE | 0.151494 | **0.151494** |

따라서 이 문서의 성능 수치는 여전히 재현 가능하고, 구 체크포인트를 대상으로 한 진단·임계값 재선정도 계속할 수 있다. 이 복구가 없었다면 관측소별 예외의 합산 효과를 잴 수 없어 [광주 한파 예외의 합산 악화](#null-calibration-overrides)를 놓쳤을 것이다.

안전장치는 두 겹으로 넣었다. `eval_cache._assert_split_matches_checkpoint()`와 `train.assert_split_matches()`가 체크포인트에 저장된 기준선과 재구성값을 대조해, 어긋나면 지표가 나오기 전에 멈춘다. 후자는 `make_split(..., ckpt=ckpt)` 경로로 **진단 스크립트 15개 전부**에 배선했다 — 그 전에는 `eval_cache`를 거치는 경로만 보호돼, 나머지는 학습에 쓴 표본이 섞인 검증셋에서 조용히 지표를 냈다.

남는 제약은 **서로 다른 알고리즘으로 학습된 두 체크포인트의 성능 비교**다. 현재 코드로 재학습한 후보를 배포본과 견주려 하면 검증셋이 서로 달라 비교가 성립하지 않고, `promote_checkpoint.py`의 회귀 성능 게이트가 이를 FAIL로 잡는다(의도된 동작이다). 따라서 **다음에 유효한 성능 개선이 나올 때 이 분할·정규화 수정과 함께 승격**하기로 했다. 그때까지 배포는 구 분할로 학습된 현재 체크포인트를 유지하며, 그 체크포인트에 대한 진단은 위 복구 덕분에 정상 동작한다.

#### 오탐으로 판명된 것

`import_kma_fileset.py`가 풍향 결측만 `0.0`으로 채우는 것이 "결측을 기본값으로 채우지 않는다" 위반으로 지적됐으나, **실측으로 확인하니 버그가 아니었다.** `wind_dir == 0.0`인 117,205건 전부가 풍속 0.4m/s 이하로, 기상학적 정온(calm) 코드다(풍향 0은 16방위 격자에 없는 별도 값이고, 북풍은 360으로 표기된다). 다만 진짜 결측이 들어오면 정온과 구분할 수 없다는 잠재 위험은 남는다.

### 점검이 닿지 않던 두 영역(2026-08-17)

지금까지의 점검은 헤드와 지표에 집중돼 있었다. 그 바깥에서 "그렇다고 서술만 하고 재본 적 없는" 두 가지를 확인했다.

#### 게이트는 Z축만 본다 — '축의 신뢰도 판단'이 아니다

헤드는 기온을 흔들어 물리적 방향성을 확인해왔지만 게이트는 그런 식으로 흔들어 본 적이 없었다(`gate_behavior_check.py`). 먼저 구조가 분명해졌다 — 게이트의 입력은 `num_x`, 즉 **Z축뿐이다**. Re축 보간장의 품질(이웃 관측이 몇 개였는지, 결측이었는지)과 Im축 경향의 품질은 배분에 반영될 수 없다. "축의 신뢰도에 따라 가중치를 조절한다"는 해석은 이 구조에서 성립하지 않으며, 게이트가 하는 일은 **"지금이 어떤 상황인가(Z)"에 따른 배분 전환**이다.

![게이트 거동](docs/images/gate_behavior.png)

그 전제 위에서 거동은 정상이다. 배분은 표본마다 실제로 달라진다(Re 표준편차 0.090, 5~95% 구간 0.347~0.635) — '입력 조건부'라는 서술이 과장이 아니다. 배분을 가장 크게 움직이는 특성은 기온(변화폭 0.553)이며, 기온이 높아지면 Re 비중이 오르고 Z 비중이 내려간다. 그다음이 강수(0.260)와 기압(0.174)이다.

> 강수형태 특성의 민감도는 **0이 아니라 측정 불가**다. 표본의 5%와 95% 백분위가 같은 값이라(대부분 '없음'에 몰려 있다) 흔들 구간 자체가 없다. 0.0000을 "게이트가 무시한다"는 증거로 읽지 않도록 스크립트가 둘을 구분해 출력한다.

#### 결측 대체값 0.5는 중립이 아니다 — 다만 지금 바꾸지 않는다

이웃 관측이 전무하면 Re축 보간장을 0.5로 채우고 이를 "중립값"이라 불러왔다(`neutral_input_check.py`). 0.5가 중립이라는 전제는 채널이 [0,1]로 정규화돼 있다는 사실에서 왔으나, **정규화 식이 채널마다 달라 0.5가 뜻하는 물리량도 채널마다 다르다.**

| 채널 | 0.5의 물리적 의미 | 실제 분포 평균 | 차이 |
|---|---|---|---|
| 기온 | 20.0°C | 0.408 (14.5°C) | −0.092 |
| 습도 | 50.0% | 0.662 (66.2%) | +0.162 |
| 기압 | 1010 hPa | 0.602 (1016.1 hPa) | +0.102 |
| **풍속** | **10.0 m/s** | **0.107 (2.1 m/s)** | **−0.393** |

풍속 채널에서 0.5는 평상시의 다섯 배에 해당하는 강풍을 뜻한다. 즉 "정보 없음"이 실질적으로 **특정 값의 주장**이 되며, 진짜 강풍 상황과 결측이 입력에서 구분되지 않는다(aliasing). Im축의 중립값 0은 문제가 없었다 — 0으로 채울 때와 채널 평균으로 채울 때의 출력 변화가 각각 +0.336°C와 +0.334°C로 실질적으로 동일하다.

**그럼에도 서빙 동작을 지금 바꾸지 않는다.** 모델은 학습 중에도 결측을 0.5로 본 상태로 학습했으므로, 0.5는 물리적 중립값은 아니지만 **모델이 배운 결측 표식**이다. 서빙에서만 대체값을 바꾸면 학습·서빙 불일치가 생긴다.

**발생 빈도를 계측한 결과 마스크 채널 도입을 보류했다.** 이웃 관측이 전무해 0.5로 채워지는 경우는 138만 건 중 **1,154건(0.083%)**에 불과했고, 이웃이 3곳 이하인 희박한 경우까지 합쳐도 0.46%다. 98.1%는 이웃 11곳을 모두 갖췄다. 정확도에 미치는 영향이 이 규모라면 입력 차원을 바꿔 재학습할 근거가 되지 않는다. 다만 **실시간 서빙에서는 API 응답이 대상 관측소 하나만 돌아올 수 있으므로** 이 경로 자체는 남아 있다 — 정확도 문제가 아니라 서빙 강건성 문제로 분류하고, 결측 시 그 사실을 화면에 표시하는 현행 처리를 유지한다.

#### 배포 판정선은 안정적이다

원본 공간의 임계값 안정성은 `threshold_validation.py`가 ±0.02 흔들기로 재고 있었으나, **판정이 실제로 이뤄지는 보정 공간에서는 재본 적이 없었다.** 등온 회귀의 평탄 구간 때문에 임계값을 조금만 옮겨도 구간 하나가 통째로 넘어가 판정이 계단식으로 바뀔 수 있어, 이 확인이 필요했다(`calibrated_threshold_check.py`).

| 헤드 | 배포 판정선 | F1 | −0.02 | +0.02 | F1 변동폭 | 판정선과 동점인 표본 |
|---|---|---|---|---|---|---|
| 폭염 | 0.389 | 0.8144 | 0.8142 | 0.8146 | 0.0004 | 0 |
| 한파 | 0.229 | 0.5071 | 0.5068 | 0.5063 | 0.0008 | 0 |
| 황사 | 0.084 | 0.1894 | 0.1863 | 0.1909 | 0.0046 | 1,588 |

최악 변동폭이 0.0046으로, 배포 동작점은 평탄 구간 위에 근접하여 놓여 있지 않다. 폭염·한파는 판정선과 정확히 같은 보정값을 갖는 표본이 하나도 없어 재선정이 깨끗하게 작동했고, 황사만 1,588건이 동점이나 F1 영향은 0.005 미만이다. (2026-08-19 갱신: 한파 판정선은 승격된 한파 헤드 기준 0.229로 재적합됐다 — 이전 값 0.224/F1 0.4608은 승격 전 헤드 기준.)

<a id="precip-ceiling"></a>

### 강수 축 상한 분석 — 남은 여유가 얼마인가(2026-08-31)

강수 축에 새 기법을 도입하기 전에 **개선 여지의 크기를 먼저 쟀다.** 결론은 남은 여유가 생각보다 작고, 그중 상당 부분이 실력이 아니라 **지표 정의에서 온다**는 것이다.

**① 달성 가능 상한.** 검증셋(276,116건, 무강수 93.8%) 실측.

| 시나리오 | MAE(mm) | 기준선 대비 |
|---|---|---|
| 상시 0 예측(기준선) | 0.1515 | — |
| 모델 원본 출력 | 0.1665 | −9.9% |
| 현행 서빙(확률 게이팅 τ=0.85) | 0.1573 | −3.8% |
| **오라클 건조판정 + 현재 amount** | 0.1363 | **+10.0%** |
| **오라클 건조판정 + 젖은구간 중앙값** | 0.1278 | **+15.6%** |

건조/강수를 완벽히 가려내도 전체 MAE 개선 상한은 **+15.6%** 다. 강수 발생 판정 자체도 여유가 없다 — `rain_prob` 로 얻을 수 있는 F1 상한이 τ=0.83 에서 0.5017 인데 현행 τ=0.85 가 0.5001 이다.

**② amount 헤드는 상수보다 나쁘다.** 젖은 구간(17,015건)만 보면 현재 헤드 MAE 2.2115, 상수(젖은구간 중앙값 1.00mm) 2.0746 이다. 헤드가 강도를 거의 표현하지 못한다.

| 실측 강수 | 표본 | 실측 평균 | 모델 평균 |
|---|---|---|---|
| 0.1~0.5mm | 5,118 | 0.210 | 0.346 |
| 1~2mm | 2,987 | 1.342 | 0.572 |
| 5~10mm | 1,442 | 6.825 | 1.202 |
| 10mm+ | 838 | **17.208** | **1.543** |

최적 전역 스케일 계수가 k=0.95 로 1 에 가까워 **스케일이 아니라 모양(shape) 문제**다.

**③ 원인 — MSE 로 학습하고 MAE 로 채점한다.** `train.py` 기본 경로는 최종 곱 출력에 전 표본 MSE 를 건다(무강수 93.8% 포함). MSE 최적해는 조건부 **평균**이고 MAE 최적해는 조건부 **중앙값**인데, 93.8% 가 0 인 분포에서 P(강수|x)<0.5 인 표본의 조건부 중앙값은 0 이다. 즉 MAE 기준 최적 예측은 대부분의 표본에서 "상시 0"(기준선)과 같아진다 — 모델은 MSE 를 옳게 최소화하는 중인데 MAE 로 채점받고 있다.

**④ 헤드라인은 게임할 수 있다 — 그러나 하지 않는다.** 날짜 블록으로 보정용/평가용을 나눠 보정용에서만 임계값과 상수를 고르고 평가용에서 채점했다.

| 방식 | 전체 MAE | 기준선 대비 | 젖은구간 조건부 MAE |
|---|---|---|---|
| 현행 서빙 | 0.1552 | −0.7% | **2.3383** |
| 상수 1.00mm + τ=0.970 | 0.1499 | +2.8% | 2.4909 |
| 혼합 α=0.15 + τ=0.970 | 0.1488 | **+3.4%** | 2.4654 |

**"기준선 미달"을 "+3.4% 상회"로 뒤집을 수 있다.** 대가는 주 지표인 젖은 구간 조건부 MAE 악화(2.3383 → 2.4654)와 강도 정보의 소실이다 — 상수 방식은 50mm 호우에도 1.00mm 를 낸다. 이 교환비는 본 저장소가 이미 내린 판단(전체 MAE 대신 조건부 MAE 와 F1 을 주 지표로 삼는다)을 정량적으로 뒷받침하므로, **채택하지 않는다.** 다만 "미달"이 능력 부족이 아니라 약 4%p 의 게임 가능한 여유이며 그것을 쓰지 않기로 선택한 결과라는 점은 명시해 둔다.

**⑤ 이 표의 용도.** 앞으로 강수 축 개선안(CSGD·분위 회귀·Tweedie 등)을 검토할 때 **먼저 이 상한과 대조한다.** 전체 MAE 로 +15.6% 이상을 약속하는 제안은 오라클 건조판정보다 낫다는 뜻이므로 의심해야 한다. 실질 개선은 젖은 구간 조건부 MAE(현재 2.34)와 강수 발생 F1(현재 0.50)에서 나와야 하며, **amount 헤드가 강도를 표현하지 못하는 문제(②)가 남은 가장 큰 실질 과제다.**

<a id="improvement-levers"></a>

### 개선 레버 측정 — 어디에 여유가 남았는가(2026-08-31)

새 기법을 도입하기 전에 **레버별로 남은 여유를 먼저 쟀다.** 네 확률 헤드에 대해 변별력(AUC)과 임계값 재선정 여유를 분해했다.

| 헤드 | 양성률 | AUC | AP | 현행 F1 | 임계값 여유 |
|---|---|---|---|---|---|
| 강수 발생 | 6.2% | 0.9141 | 0.4964 | 0.5001 | +0.0015 |
| 폭염 | 23.2% | 0.9624 | 0.8946 | 0.8139 | +0.0022 |
| 한파 | 6.0% | 0.8775 | 0.5115 | 0.4987 | +0.0040 |
| 황사 | 3.1% | 0.8238 | 0.1126 | 0.1906 | +0.0036 |

"임계값 여유"는 임계값을 최적으로 다시 골랐을 때의 F1 증가분이다.

**① 후처리 레버는 소진됐다.** 네 헤드 모두 임계값 재선정으로 얻을 수 있는 것이 +0.004 이하이고, 확률 보정도 이미 적용되어 ECE 가 0.002~0.005 수준이다. 따라서 임계값·보정·손실 재가중 계열의 기법으로는 F1 을 의미 있게 움직일 수 없다.

**② 남은 레버는 변별력(AUC)뿐이며, 그것은 새 입력이나 실질적으로 더 나은 모델을 요구한다.** AUC 가 낮은 순으로 여지가 크다.

- **황사(0.824)** — 가장 낮고, 관측소별로도 0.745~0.827 로 고르게 낮다. 본 문서가 이미 서술한 구조적 진단(PM10 은 국외 장거리 수송이 지배하는데 입력은 국내 12지점 지상관측에 한정)과 이 측정이 일치한다. 외부 에어로졸 자료가 사실상 유일한 레버다.
- **한파(0.878)** — 중간 수준의 여지.
- **강수 발생(0.914)** — 변별력 자체는 양호하다. F1 0.50 은 탐지 실패가 아니라 양성률 6.2% 의 귀결이다(정밀도 0.488·재현율 0.513).
- **폭염(0.962)** — 거의 포화 상태다.

**③ 방법으로 고칠 여지가 확인된 곳은 회귀 쪽에 하나 남았다.** 위 표는 전부 분류 헤드다. AUC 로 측정되지 않는 축에서, [강수 축 상한 분석](#precip-ceiling)이 밝힌 **amount 헤드의 강도 표현 실패**(10mm 이상 구간에서 실측 17.2mm 대비 모델 1.54mm, 상수보다 나쁨)가 유일하게 남은 명확한 방법론적 공백이다.

<a id="input-expansion-2026-08-31"></a>

### 입력 확장 두 시험 — 둘 다 기각(2026-08-30~31)

관측망 **바깥**의 정보를 넣으면 나아지는지 두 갈래로 시험했다. 둘 다 단순 프로브(로지스틱/GBM 분류기)에서는 이득이 예측됐으나 **전체 파이프라인 재학습에서는 재현되지 않았다.** 판정에는 이번에 새로 만든 `bootstrap_ci_compare.py`(날짜 블록 짝지은 부트스트랩, B=2,000)를 썼다 — 점추정치 비교만으로 채택·기각을 결정하지 않기 위해서다.

**① Re축 격자에 이웃 강수 채널 추가(4→5ch).** `data_expansion_probe.py`에서 "이웃 현재값"(강수 포함) 단계가 ΔAUC +0.0254로 컸는데, 배포 중인 4채널 격자(기온·습도·기압·풍속)에는 강수가 아예 없었다. sqrt 압축 정규화로 5번째 채널을 붙여 대조 실험(동일 SEED, `RE_CHANNELS`만 변경)했다.

| 지표 | Δ(처리−대조) | 95% CI | 유의 |
|---|---|---|---|
| 기온 MAE | −0.0575°C | [−0.068, −0.047] | **개선** |
| 강수 MAE | +0.0021mm | [−0.001, +0.005] | — |
| 폭염 F1 | −0.0103 | [−0.022, +0.001] | — |
| 한파 F1 | −0.0157 | [−0.040, +0.008] | — |
| 황사 F1 | −0.0245 | [−0.037, −0.012] | **악화** |

**기각.** 기온 개선은 실제이나 황사 악화도 실제다. 황사 헤드는 정밀도 자체가 낮아도 [Re축 게이트 학습을 견인하는 구조적 역할](#dust-head) 때문에 유지 중이라, 그 악화를 감수할 수 없다. 처음에는 "이득 1개 대 손해 4개"로 기각했으나 부트스트랩 CI 재검증 결과 강수·폭염·한파 악화는 **재표본 노이즈 범위 안**이었다 — 기각 결론은 유지하되 사유를 정정했다. 사후 진단(`re_axis_channel_saliency.py`, 채널별 그래디언트 노름)에서 강수 채널은 죽어 있지 않았고 오히려 전 표본군에서 가장 큰 그래디언트를 받고 있었다.

**② 서해 도서 AWS 13개 지점 강수를 Z축 특징으로 추가(26차원).** 도서 관측소가 인천보다 서쪽 112~424km에 있고 그 거리가 이류 지연으로 역산한 상류 거리(약 404km)와 겹친다는 가설에서 출발했다. 절제 실험은 ΔAUC +0.0143으로 게이트(+0.005)를 3배 가까이 넘었다. 데이터는 `collect_island_backfill.py`로 2022-01~현재를 채웠다(`awsh.php`는 단일 시각 호출로 전 지점을 돌려주므로 관측소당이 아니라 시각당 1회면 된다).

| 지표 | Δ(처리−대조) | 95% CI | 유의 |
|---|---|---|---|
| 기온 MAE | +0.0495°C | [+0.039, +0.061] | **악화** |
| 강수 MAE | +0.0002mm | [−0.003, +0.004] | — |
| 폭염 F1 | −0.0154 | [−0.028, −0.003] | **악화** |
| 한파 F1 | +0.0206 | [−0.030, +0.065] | — |
| 황사 F1 | −0.0659 | [−0.092, −0.039] | **악화** |

**기각.** 유의한 변화 셋이 전부 악화이고, 유일하게 좋아 보인 한파는 노이즈 범위였다. 게이트 축 배분이 대조군 Re 0.452/Im 0.230/Z 0.318에서 처리군 Re 0.103/Im 0.308/Z **0.589**로 이동했다 — Z축에 특징 26개를 붙이자 게이트가 Z로 쏠리며 Re축(공간 정보)이 45%→10%로 무너졌고, 공간 분포가 거의 유일한 단서인 황사가 가장 크게 다쳤다는 해석과 방향이 맞는다(메커니즘 자체는 검증하지 않은 가설이다).

코드는 재현 가능하도록 남겼다 — `RE_CHANNELS`(기본 4), `USE_ISLAND`(기본 0), `island_collector.py`. **교훈: 단순 프로브의 절제 실험 결과는 공유 게이트·트렁크·경쟁하는 헤드가 있는 전체 파이프라인에서 재현된다는 보장이 없다.** 두 시험 모두 같은 방식으로 어긋났다.

## 아키텍처(Architecture)

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 입력 — 지상 관측 실측값(시뮬레이션·추정치는 입력으로 쓰지 않는다)             │
├────────────────────────┬────────────────────────┬────────────────────────┤
│ Re · 주변 상태          │ Im · 변화 추세          │ Z · 현재 상태          │
│ 이웃 11개 관측소        │ 동일 관측소             │ 대상 관측소             │
│ IDW 공간보간장          │ 1·3·6h 전 대비 변화량   │ 수치 관측값             │
│ 4ch × 32 × 32          │ 12차원                  │ 14차원                 │
└────────────┬───────────┴────────────┬───────────┴────────────┬───────────┘
             ▼                        ▼                        ▼
     ┌───────────────┐        ┌───────────────┐        ┌───────────────┐
     │   Re 인코더    │        │   Im 인코더   │        │   Z 인코더     │
     │   소형 CNN     │        │   프로젝션    │        │      MLP      │
     └───────┬───────┘        └───────┬───────┘        └───────┬───────┘
             │ Re (64d)               │ Im (64d)               │ Z (64d) = v_Z
             └────────────────┬───────┴────────────────────────┴──┐
                              ▼                                   │
         ┌─────────────────────────────────────────┐              │
         │ ModalityGate — 입력 조건부 softmax 배분  │              │
         │ w_Re + w_Im + w_Z = 1 (출력마다 재계산)  │              │
         └────────────────────┬────────────────────┘              │
                              ▼                                   │
         ┌─────────────────────────────────────────┐              │
         │ 융합(Eq.1) — 원소별 Hermitian modulus    │              │
         │ s = √((w_Re·Re)²+(w_Im·Im)²+(w_Z·Z)²)   │              │
         │ 64차원 · 제곱이 부호를 없앤다             │              │
         └────────┬───────────────────────┬────────┘              │
                s │                     s │  v_Z(부호 보존)        │
                  ▼                       ▼ ◀─────────────────────┘
        ┌───────────────────────────┐ ┌────────────────────────────────┐
        │ 회귀 헤드 2                │ │ 분류 헤드 3                     │
        │ 기온 Δ · 퍼시스턴스 잔차    │ │ 폭염 · 한파 · 황사              │
        │ 강수 · 허들(Hurdle) 구조   │ │ 입력 [s, v_Z] = 128차원         │
        └───────────────────────────┘ └────────────────────────────────┘
```

도식의 오른쪽 세로선이 이 구조에서 가장 중요한 경로다. Z 인코더의 출력 `v_Z`는 융합을 **거치지 않고** 분류 헤드로 직접 내려간다. 융합식이 제곱을 거치며 부호를 없애기 때문이며, 이 경로가 없으면 헤드가 `|편차|`만 보고 한겨울에 폭염 확률을 올린다([계절 오탐](#seasonal-false-alarm) 참조). 회귀 헤드는 이 경로를 받지 않는다 — 강수량은 항상 0 이상이라 부호 문제가 없고, 실제로 부호 표현을 주자 성능이 악화되어 기각했다.

3축은 각각 상이한 질문에 답하며, 그 답을 하나로 융합(fusion)한다.

| 축 | 질문 | 입력 | Z축만으로 유도 불가능한 이유 |
|---|---|---|---|
| **Z**(현재 상태) | 이 지점은 현재 어떤 상태인가 | 기온·강수·습도·풍속·풍향(sin/cos)·기압·강수형태·시각(sin/cos)·위도·경도·연중 시각(sin/cos) = 14차원 | — (기준축) |
| **Re**(주변 상태) | 주변 지역은 현재 어떤 상태인가 | 대상 관측소를 제외한 11개 관측소의 동일 시각 실측값을 IDW(역거리가중, power=2)로 ±3°(약 300km) 격자 32×32에 보간, 4채널(기온·습도·기압·풍속) | 타 지점의 관측값은 이 지점의 단일 스냅숏(snapshot)에 존재하지 않는다 |
| **Im**(변화 추세) | 어느 방향으로 변화하는 중인가 | 동일 관측소의 1·3·6시간 전 대비 변화량 × 4변수 = 12차원 | ∂s/∂t는 단일 시점 s(t) 하나만으로는 계산할 수 없다 |

- **융합**: 원 논문 Eq.1의 Hermitian-style modulus를 원소별(element-wise)로 적용하여 길이 64 벡터 `s`를 생성한다.
- **축 가중치**: 고정 상수가 아니라 `ModalityGate`(14→16→3, softmax)가 출력마다 재계산한다. Σw=1로 고정하여 스케일 자유도를 제거한다. 입력 차원은 Z축 수치 벡터의 차원과 같다 — 게이트는 Z축만 보며, Re·Im축의 품질은 배분에 반영되지 않는다([점검이 닿지 않던 두 영역](#unchecked-areas) 참조).
- **회귀 헤드**: 기온은 퍼시스턴스 잔차(residual) 방식, 강수는 허들(Hurdle) 구조 `σ(z₁) × softplus(z₂)`를 사용한다.
- **분류 헤드**: 폭염·한파·황사 3종, 각각 독립된 이진 교차 엔트로피(BCE)를 사용한다. 대설은 한파∧호우의 논리곱(AND)에 해당하여 중복 계산이 되므로 별도 헤드로 두지 않는다.

배포 체크포인트의 파라미터는 총 60,057개다 — Re 인코더 28,112 · Im 인코더 10,176 · Z 인코더 2,656 · 게이트 291 · 헤드 5종 18,822(기온·강수·강수확률 각 2,113, 극한기상 각 4,161). 극한기상 헤드가 회귀 헤드보다 두 배 가까이 큰 것은 입력이 `s` 단독(64차원)이 아니라 `[s, v_Z]`(128차원)이기 때문이다. Re 인코더가 ResNet18(1,100만)에서 2.8만으로 줄어든 경위는 [한계 3](#3-정적-축-가중치는-무용한-축을-억제하지-못했다)을 참조한다.

### Docker로 대시보드만 실행

로컬 GPU 환경에서 학습을 사전에 완료했다고 가정한다 — 이미지에는 체크포인트를 포함하지 않으며, 실행 시 볼륨으로 마운트한다(`Dockerfile` 상단 주석 참조).

```bash
docker build -t tri-chef-app .
docker run -p 8501:8501 \
  -v "$(pwd)/checkpoints:/app/checkpoints" \
  -v "$(pwd)/cache:/app/cache" \
  --env-file .env \

**코드 수정 사항을 즉시 반영하려는 경우** — 위 명령은 이미지에 포함된 소스를 사용하므로, `.py` 파일을 수정해도 실행 중인 화면에는 반영되지 않는다(재빌드가 필요하다). 화면 문구나 로직을 수정하며 확인하려면 소스 디렉터리도 함께 마운트한다.

  -v "$(pwd):/app" \
  --env-file .env \
  tri-chef-app
```

이 방식으로 실행하면 파일을 저장할 때마다 Streamlit 우측 상단에 "Source file changed"가 표시되며, Rerun을 누르면 즉시 반영된다(항상 자동 반영하려면 ⋮ → Settings → Run on save).

### API 트래픽 — 5분 갱신 주기가 부하로 이어지지 않는 이유

출력값 1건당 API 15회 호출이 필요하다. 대상 관측소 1 + 인접 11곳(Re축 공간보간장) + 대상 관측소의 과거 1·3·6시간(Im축 경향벡터) = 15회. 화면은 +6시간과 +12시간을 함께 표시하므로 갱신 1회에 산출값 2건, 즉 **30회**가 든다(위 [호출량](#1-호출량--산출값-1건당-api-15회-화면-1회-갱신당-30회) 참조).

문제는 이 비용이 접속자 수와 갱신 횟수의 곱으로 증가한다는 점이다. 해당 인증키는 누적 약 9,800건에서 차단된 이력이 있어(2026-08-07 확인), 대책 없이는 이틀 내 재차단될 수 있다. 대시보드 기본 갱신 주기가 5분일 때의 계산은 다음과 같다.

| 조건 | 시간당 호출 | 일일 호출 |
|---|---|---|
| 캐시 없음, 5분 갱신, 관측소 1개 | 12회 × 30 = **360** | **8,640**(차단 지점 근접) |
| 캐시 없음, 5분 갱신, 접속자 3명 | 1,080 | 25,920(**차단 지점 초과**) |
| **캐시 적용**(관측소·관측시각·리드타임 단위) | **30** | **720** |

핵심은 ASOS가 매시 정각에 1회만 관측하며, 그 값을 약 10분 후 공개한다는 물리적 사실이다. 동일 정시 내에서는 재조회해도 서버가 동일한 값을 반환한다. 이에 `app.py`가 출력값을 (관측소, 관측시각, 리드타임) 키로 캐시한다.

```python
@st.cache_data(ttl=3600, show_spinner="관측 조회 중... (12개 관측소)")
def cached_predict(stn: str, obs_hour: str, lead_hours: int, _model, _ckpt) -> dict:
    return predict(stn=stn, model=_model, ckpt=_ckpt)
```

`lead_hours`를 캐시 키에 반드시 넣어야 한다. Streamlit은 언더스코어 접두 인자(`_model`·`_ckpt`)를 해시 대상에서 제외하므로, 이 인자가 없으면 키가 `(stn, obs_hour)`뿐이라 +6시간 호출과 +12시간 호출이 같은 캐시 항목을 공유한다 — 먼저 계산된 쪽의 결과를 나중 호출이 그대로 돌려받는다(2026-08-18 +12시간 추가 시 확인).

- 호출량이 갱신 주기·접속자 수와 무관하게 시각에만 종속된다.
- 관측소당 시간당 30회가 절대 상한이므로, 12개 관측소를 매시간 전부 조회해도 최악의 경우 일일 8,640회다. 다만 아래 일일 상한(3,000)이 그 전에 폴백으로 전환시킨다.
- 실사용(관측소 1~2개)에서는 일일 720~1,440회로, 차단 지점의 7.3~14.7%다.

실측 검증: 동일 정시에 2회 실행 시 1회차 30건, 2회차 누적 30건(증가 0건)으로 확인되었다.

2차 안전장치로 프로세스 단위 일일 상한(`KMA_DAILY_CALL_BUDGET`, 기본값 3,000)을 둔다. 상한 초과 시 예외 대신 폴백으로 전환하며, 사용량은 사이드바에 실측값으로 표시한다. 상한을 5건으로 강제한 실험에서 호출 5건 / 차단 10건으로 의도된 동작을 확인했다.

**일일 예산 합산**: 대시보드 720~1,440회 + GitHub Actions 데이터 갱신 288회 ≈ 1,000~1,700회/일 — 차단 지점(9,800)의 10~17% 수준이다.

## 데이터 갱신 파이프라인

배포 화면이 보는 관측 데이터가 어떻게 최신으로 유지되는가. 위 절이 "호출량"을 다뤘다면 이 절은 "갱신 경로"를 다룬다.

**저장소가 원본이다.** Streamlit Cloud의 컨테이너 파일시스템은 휘발성이므로 앱이 기록한 파일은 재시작 시 소실된다. 이에 갱신 주체를 앱이 아닌 저장소로 설정한다. `.github/workflows/refresh-data.yml`이 15분마다 `refresh_deploy_data.py`를 실행하여 ① 최근 관측 창을 갱신하고 ② 적중률 로그의 대기 항목을 실측값과 대조하며 ③ API 사용량을 기록한 후, 결과를 커밋한다. 이 워크플로 역시 `KMA_API_KEY` 시크릿이 필요하다(회당 API 호출은 가변적이나 일일 약 288건 — 격차 보충 방식이라 주기와 무관하게 일정하다).

**재배포와 최신성을 분리했다(2026-08-20).** 이전에는 main에 커밋했고, Streamlit Cloud가 그 push를 감지해 자동 재배포하면서 신규 데이터를 반영했다 — 최신성을 올리려면 재배포도 그만큼 자주 겪어야 하는 구조였다(재배포마다 캐시 소실·수십 초 끊김). 그래서 2026-08-19에는 6시간→2시간으로만 절충했다.

ASOS 관측 자체가 매시 정각 1회, 10분 후 공개가 물리적 상한이라 이보다 훨씬 자주 갱신해봐야 새 데이터가 없다는 점에 착안해, 갱신 대상을 **`data`라는 별도 브랜치**로 옮겼다. Streamlit Cloud는 `main`만 감시하므로 `data`에 아무리 자주 커밋해도 재배포가 걸리지 않는다. 대신 `app.py`가 `load_merged_history()`에서 로컬 디스크 대신 `raw.githubusercontent.com`의 `data` 브랜치 파일을 직접 읽는다(5분 캐시). 이 구조로 갱신 주기를 15분까지 줄일 수 있었다 — ASOS 공개 지연(10분)을 감안해도 새 관측을 최악 25분 안에 반영한다. `main`의 `cache/*.json`은 더 이상 이 워크플로가 갱신하지 않으며, raw 조회가 실패할 때만 쓰는 최후 폴백으로 남는다.

대가는 `data` 브랜치 히스토리가 하루 수십~백여 커밋씩 쌓인다는 점이다. 파일 자체가 작고(0.6MB 안팎) 워크플로가 얕은 클론(depth 1)만 쓰므로 현재는 문제가 안 되지만, 커밋이 수만 건 누적되면 재검토가 필요하다.

<a id="history-fallback"></a>

### 관측 이력 창 조회의 3단 폴백(2026-08-23)

위 구조에서 `main`의 로컬 스냅숏은 **재배포 시점에 멈춘 값**이 된다. 그런데 초기 구현은 raw 조회가 한 번만 실패해도 곧장 그 스냅숏으로 내려갔고, 화면에는 "관측 이력 창이 N시간 지연됐다"는 **하나의 문구**만 표시했다. 원인이 "`data` 브랜치 갱신 지연"인지 "raw 조회의 순간적 실패"인지 구분되지 않아, 실제로는 며칠 묵은 값을 보면서도 갱신 경로를 의심하게 되는 구조였다.

조회 경로를 3단으로 나누고, 어느 단계까지 내려갔는지를 문구로 구분한다.

| 단계 | 출처 | 화면 표시(최신 관측이 2시간 이상 지연된 경우) |
|---|---|---|
| ① `raw` | `data` 브랜치의 `recent_window.json`. 8초 타임아웃, 1초 대기 후 1회 재시도 | 갱신 경로(GitHub Actions 실행 이력) 점검을 안내 |
| ② `last_good_fallback` | 이 프로세스가 마지막으로 성공한 raw 조회 결과(`st.cache_resource` 보관) | raw 조회가 상당 시간 계속 실패 중임을 안내 |
| ③ `local_fallback` | `main`의 `cache/recent_window.json` 디스크 스냅숏 | 이 프로세스가 뜬 뒤 raw 조회가 **한 번도** 성공하지 못했음을 안내 |

재시도를 1회로 제한한 이유는 이 조회가 페이지 렌더링을 동기적으로 막기 때문이다 — 재시도를 늘리면 그대로 체감 지연이 된다. ②를 ③보다 앞에 둔 이유는 최신성 때문이다. ②는 최악의 경우에도 "이 프로세스가 뜬 이후 raw 조회가 마지막으로 성공한 시점"까지만 묵지만, ③은 마지막 재배포 시점에 고정되어 있다.

**15분 주기는 GitHub Actions 자체의 `schedule`이 아니라 별도 Cron 트리거가 지킨다(정정, 2026-08-20).** `data` 브랜치 분리로 재배포 부담 없이 15분 주기를 설정할 수 있게 된 뒤에도, 배포 화면에 "관측 이력 창의 최신 데이터가 2시간 넘게 지연됐다" 경고가 반복됐다. GitHub Actions API로 실행 시각을 대조해보니 원인은 GitHub 자체에 있었다 — `schedule:` 이벤트는 15분처럼 짧은 주기를 지키지 못했다(고부하 시간대 지연은 GitHub 공식 문서에도 명시됨). 15분 주기 전환 직후 실측 실행 간격이 20~81분이었다(워크플로는 항상 성공했지만 GitHub이 애초에 그 시각에 실행을 시작해주지 않았다). 그래서 `cloudflare-worker/`의 Cloudflare Cron Trigger가 GitHub REST API의 `workflow_dispatch`를 15분마다 직접 호출하도록 바꿨다 — GitHub Actions 러너 큐와 무관하게 동작해 정시성이 훨씬 높다. `refresh-data.yml`의 `schedule:`은 이 경로가 죽었을 때만 대신하는 55분 안전망으로 완화했다. 호출에 쓰는 GitHub PAT은 이 저장소 하나에 "Actions: write" 권한만 준 fine-grained 토큰이라, 유출돼도 워크플로 실행 남발 이상의 피해가 없다(코드·다른 시크릿 읽기 권한 없음).

이 워커를 세우는 과정에서 도구 쪽 함정을 하나 만났다. **`... | npx wrangler secret put KEY`는 값이 전달되지 않은 채 빈 문자열을 등록한다 — `npx`가 파이프로 들어온 표준입력을 가로채기 때문이다.** 그런데도 CLI는 `✨ Success! Uploaded secret KEY`를 출력하고 `wrangler secret list`에도 이름이 뜨므로 겉으로는 성공과 구분되지 않는다. 그 결과 워커에서 `env.GITHUB_PAT`이 빈 문자열이 되어 GitHub이 401 Bad credentials로 거부했다. 값 대신 길이와 SHA-256 지문만 돌려주는 임시 진단 경로를 워커에 두고서야 확인했다(길이 0, 빈 문자열의 해시값과 일치).

**이 원인 규명은 한 번 틀렸다가 정정한 것이다.** 처음에는 "버전을 고정하지 않고 받은 wrangler 4.x의 결함"으로 판단하고 그렇게 문서에도 적었다. 실패한 시도가 모두 `npx --yes`(최신 4.x)였고 성공한 시도가 모두 로컬 3.x 바이너리 직접 호출이었기 때문인데, **두 조건이 함께 바뀌고 있었다.** 나중에 같은 값(`abcdefghij`, 10자)을 두 경로로 나눠 등록해 대조하고서야 갈렸다 — `npx` 경유는 런타임 길이 0, 바이너리 직접 호출은 10. 즉 버전은 교란 변수였고 진짜 원인은 `npx`였다. 교훈이 둘이다. 하나는 CLI가 "성공"이라고 말하는 것과 그 설정이 런타임에 실제 반영되는 것은 별개이며 이 간극은 런타임에서 값을 직접 확인해야만 드러난다는 것. 다른 하나는 두 조건이 동시에 바뀐 관찰에서 한쪽만 원인으로 지목하면 안 되고, 조건을 하나씩만 바꿔 대조해야 한다는 것이다(이 저장소가 모델 실험에 적용해온 원칙을 정작 도구 문제에는 적용하지 않았다).

최종 검증은 사람이 개입하지 않은 순수 자동 Cron 실행이 GitHub Actions에 `workflow_dispatch` 실행을 성공적으로 생성하는 것으로 확인했다(2026-08-20 11:45 UTC — 이전 토큰이 이미 폐기된 상태였으므로 새 토큰이 실제로 쓰였다는 증거이기도 하다).

**공개 범위.** Community Cloud 앱은 기본값이 공개 URL이다. 기상산업진흥법상 예보업 등록 대상에 해당하지 않으려면 앱 설정에서 뷰어 허용목록(Private)으로 제한할 것을 권장한다 — 상세 내용은 아래 "법적 범위" 항목을 참조한다.

<summary><b>2. Gram-Schmidt 직교화(orthogonalization)는 본 도메인에서 손해였다</b></summary>

원 논문은 검색 과제에서 축 독립성(직교성)을 전제하나, 실측 결과(당시 `ablation.py`, 현재 `삭제예정/`으로 이동) 직교화를 강제하면 성능이 저하되었다. 네트워크가 자유롭게 학습한 Re-Im 상관도(0.48)가 오히려 회귀 성능에 기여하고 있었다 — 축 간 정보 공유가 강건성(robustness)으로 작용하는 회귀 과제와, 독립성 자체가 변별력인 검색 과제는 성격이 다르다. 기본값을 `ORTHOGONALIZE = False`로 되돌렸다.

<details id="3-정적-축-가중치는-무용한-축을-억제하지-못했다">
<summary><b>3. 정적 축 가중치는 무용한 축을 억제하지 못했다</b></summary>

학습 가능한 α/φ(로그 파라미터)는 정보가 없는 위성 축의 가중치를 오히려 증가시켰다(α 0.4→0.665). 원인은 두 가지다. 원 논문의 기본값 자체가 위성 축을 우선하는 초기화였고, ResNet18(1,100만 파라미터)이 학습 표본(572개)을 암기하여 훈련 손실 기준으로는 "가장 적합한 축"처럼 보였다. `ModalityGate`(균등 초기화 + 엔트로피 정규화 워밍업)와 인코더 축소(2.8만 파라미터)로 해결했다.

<details id="4-1시간-예보는-무의미했으며-강수는-여전히-기준선에-미달한다">
<summary><b>4. 1시간 예보는 무의미했으며, 강수는 여전히 기준선에 미달한다</b></summary>

1시간 후 기온은 퍼시스턴스(T(t+1)≈T(t))가 실질적으로 우위에 있어, 어떤 모델을 적용해도 유의미한 개선이 관측되지 않았다(+0.7%). 예보 시계(lead time)를 6시간으로 확장하자 시각(일주기) 특성과 축 융합이 실질적으로 기여하기 시작했다. 이 결과에 따라 `lead_hours = 6`으로 확정했다.

> 위 +0.7%는 초기 30일 수집본(검증셋 1,709개) 기준 측정값이다. 현행 3.5년 데이터셋(검증셋 약 66,000개)에서 재측정한 값이 아니므로, 예보 시계 선정의 근거로만 인용하며 현재 성능 수치로는 사용하지 않는다.

가장 큰 실패 항목이며, 은폐하지 않고 화면에 표시한다. 강수는 대부분의 시각이 0mm이므로, 별도 계산 없이 "항상 0mm"로 응답해도 MAE가 매우 낮게 산출된다. 원본 모델 출력의 강수 MAE는 이 기준선을 넘어서지 못했다(−9.9%). 다만 격차는 계속 줄어왔다 — 초기 −25.6%에서 가중치 조정으로 −19.3%, 검증 방식 정정 후 −17.9%, 극한기상 헤드에 부호 표현을 추가한 2026-08-17에 −9.9%가 되었고, [확률 게이팅](#precip-prob-gate)을 적용한 2026-08-29 서빙 값은 −3.8%까지 좁혀졌다(모델 재학습 없이 후처리만 바꾼 결과).

원인은 구조적으로 규명되었다. 극한기상 헤드가 3개(폭염→한파→황사)로 증가하면서, 헤드들이 하나의 공유 표현(`s`)을 두고 경쟁하여 허들 구조의 무강수 억제력이 약화되었다(기준선 대비 −16.0%에서 −25.6%로 악화). `EXTREME_BCE_WEIGHT`를 1.0에서 0.3으로 낮춰 −19.3%까지 완화했으며, 추론 후처리로 0.2mm 미만을 0으로 반올림해 잔여 손실을 축소했다. 신규 헤드 추가 시마다 강수 MAE를 재확인하는 것이 본 프로젝트의 규칙이 된 배경이다. 2026-08-17 극한기상 헤드에 별도 입력(부호 표현)을 주자 격차가 −9.9%까지 좁혀졌다 — 헤드들이 필요한 정보를 공유 표현 밖에서 얻게 되어 경쟁이 완화된 것으로 해석하며, 이 진단이 옳았음을 뒷받침한다.

> **이 서술은 같은 날 정교화되었다.** 헤드를 하나 빼면 경쟁이 줄어 강수가 좋아질 것이라는 예측을 시험했으나 정반대로 크게 악화됐다(황사 헤드 제외 시 −22.8%). 헤드 추가가 항상 손해인 것이 아니라 **공유 표현을 두고 경쟁하는 헤드만 손해이고, 특정 축의 학습을 견인하는 헤드는 이득**이다. 상세 내용은 [기각한 시험 — 황사 헤드 제외](#기각한-시험--황사-헤드-제외2026-08-17)를 참조한다.

강수는 MAE보다 "강수 발생 여부의 적중 여부"가 실용적 가치에 가까우며, 이는 대시보드 '성능 검증' 탭의 강수 적중률(0.1mm 기준 이진 판정 일치)로 별도 제시한다.

**2026-08-17 구간 분해로 원인을 특정했다(이후 구조가 바뀌었다 — 아래 참조).** 당시 격차는 강수량을 못 맞혀서 생긴 것이 아니었다 — 1mm 이상 전 구간에서 모델은 기준선을 이겼고, 표본의 93.8%인 무강수 구간에서 softplus가 정확한 0을 내지 못해 깔리는 평균 0.032mm가 전체 격차의 201%를 만들었다. **그러나 2026-08-29 강수 확률 게이팅 배포 이후 이 구조는 해소됐다** — 현재 오차 출처는 무강수 12.3% / 강수 87.7%로, 남은 격차는 강수 구간의 강도 예측이 지배한다([강수 축 상한 분석](#precip-ceiling)). 상세 수치와 후처리 임계값 재산출 결과는 [지표 분리 측정과 오차 분해](#metrics-and-breakdown)를 참조한다.

> 기준선 수치는 과거에는 학습 시 계산만 하고 체크포인트에 저장하지 않아 화면에서 직접 비교하지 못했다. `train.py`에 `val_temp_naive_mae`·`val_precip_naive_mae` 저장을 추가한 이후 재학습한 현행 체크포인트부터는 두 값이 저장되어 있으며, 대시보드 '성능 검증' 탭에 기준선 대비 증감으로 표시된다.

<details id="debug-found-bugs">
<summary><b>5. 본 프로젝트의 디버깅 과정에서 발견한 실제 오류</b></summary>

- `torch.clamp(x, 0, 200)`이 x<0 구간에서 gradient가 정확히 0이 되어, 강수 예측 헤드가 전 표본 음수로 수렴한 후 학습이 영구 중단됨(`softplus`로 교체).
- 기온 손실(σ²≈수십 규모)이 강수 손실(O(1))을 1000배 압도하여 강수 헤드가 실질적으로 학습되지 않음(분산 정규화로 해결).
- 기준선을 검증셋이 아닌 전체 데이터로 계산하여, 표본 차이만으로 개선처럼 보이는 허위 결과가 발생함(검증셋 동일 표본으로 수정).
- 다중 관측소 확장 시 관측소 경계에서 서울 관측값과 부산의 6시간 후 관측값이 우연히 짝지어질 수 있는 경로가 존재함(관측소 코드 일치 조건을 추가해 원천 차단).
- 테스트 스크립트가 실패 항목을 화면에 출력만 하고 종료 코드는 항상 0을 반환하여, 항목이 실패해도 CI가 항상 통과로 표시됨(`sys.exit(0 if n_pass == n_all else 1)` 추가). 테스트를 CI에 연결하는 것과 CI가 그 결과에 실제로 반응하는 것은 별개의 문제였다.
- 적중률 로그 저장이 배포판에서 `FileNotFoundError`로 실패함(2026-08-13 확인). 원자적 저장을 의도했으나 `tmp = path + ".tmp"`라는 고정 임시 파일명을 사용했는데, Streamlit Cloud는 세션(브라우저 탭)마다 스레드를 생성하고 5분마다 이 저장을 호출한다. 두 스레드가 동일한 tmp에 기록하다 한쪽이 `os.replace`로 먼저 이동시키면, 나머지 쪽은 직전까지 존재하던 파일을 잃고 실패한다. `tempfile.mkstemp()`로 호출마다 고유한 tmp를 사용하도록 수정했다. `os.replace`의 원자성과 저장 절차 전체의 원자성은 별개의 문제였다 — 위 CI 사례와 동일한 유형의 오류였다.
- 위 오류 수정 이후에도 조용한 유실 경로가 남아 있었다. `record_prediction`/`resolve_pending`은 읽기→수정→쓰기 3단계로 구성되나 그 사이를 보호하는 락(lock)이 없어, 두 세션이 거의 동시에 읽으면 나중에 쓰는 쪽이 앞선 항목을 덮어쓴다. 충돌이 아니라 로그가 소리 없이 소실되는 문제라 증상으로 드러나지 않는다(`threading.Lock`으로 3단계 전체를 묶어 해결, 30스레드×30회 동시 호출에서 900건 전량 보존을 확인했다).
- (2026-08-16) 배치 크기를 32에서 1024로 확대하며 학습률도 √k배(5.66배) 상향한 결과, 강수·황사 성능이 실제로 저하되었다. 대조군(배치만 변경하고 마스킹은 동일) 없이 관측했다면 "13년 확장의 부작용"으로 오판했을 것이다. 배치는 유지하고 학습률만 원래 값(1e-3)으로 복원하자 성능이 회복되었다 — 배치 크기가 아니라 학습률 스케일링 규칙 자체가 본 모델에 과했다(`train.py`의 `BATCH_SIZE`/`TRAIN_LR`를 환경변수로 분리).
- (2026-08-16) 학습 로그의 최종 요약이 실제 저장된 체크포인트 값과 상이했다. 요약 출력이 `best_temp_only`(기온이 최적이었던 에폭 값)를 표시했으나, 체크포인트에는 `val_score`(기온+강수 결합 지표)가 최적이었던 에폭이 저장된다. 두 에폭이 다르면 로그에는 어느 체크포인트도 실제로 산출한 적 없는 조합이 표시된다(13년 재학습에서 로그는 기온 1.3290°C를 표시했으나 실제 저장값은 1.3551°C였다). 요약이 체크포인트의 실제 값을 표시하도록 수정했으며, 두 값이 상이하면 참고 문구를 별도로 추가한다.
- (2026-08-16) 적중률 로그가 예측을 생성한 모델을 구분하지 않았다. 체크포인트 교체 시 이전 모델 기록과 신규 모델 기록이 동일 로그에 혼재되어, "누적 적중률"이 어느 모델의 성능도 아닌 혼합값이 되었다. 예측마다 `model_id`(체크포인트 수정 시각+파일 크기)를 태그하고, 화면은 현재 배포된 모델의 기록만 집계하도록 수정했다.
- (2026-08-16) `backtest_accuracy.py`가 학습에 사용된 표본까지 포함하여 적중률을 산출하고 있었다. 화면 캡션은 "실제 운영 시각에 실제 조회 가능했던 데이터로 산출한 값"으로 설명하나, 백테스트 시딩은 검증·학습을 구분하지 않고 전체 데이터를 모델에 통과시켰다 — 동일 시점에 발견한 일 단위 라벨 누수(9번 항목)와 동일 유형의 문제다. 체크포인트가 실제로 학습에 사용한 분할의 검증 인덱스만 사용하도록 수정했다.
- (2026-08-16) 위 백테스트 시딩이 검증용 27만 건을 그대로 적중률 로그(`cache/accuracy_log.json`)에 병합하여, 파일이 73MB까지 증가해 GitHub 권장 상한(50MB)을 초과했다. 6시간마다 자동 커밋되는 파일이므로 방치 시 하드 리밋(100MB)에 도달해 조용한 CI 실패를 유발할 수 있었다. 시딩 데이터는 로컬 전용 파일로 분리하고 실시간 온라인 기록만 유지하여 12KB로 복원했다.

- (2026-08-17) 배포 중이던 모델의 폭염 헤드가 한겨울에 작동했다. 실제 −15°C 이하 관측 809건 중 85.7%에서 폭염 확률이 0.5를 넘었다. 원인은 융합 수식 `s=√((w·v)²)`가 제곱을 거치며 부호를 없애는 것이다 — 모든 헤드가 `|편차|`만 보므로 극단적 저온과 극단적 고온이 같은 크기로 들어온다. 회귀 기온 헤드가 퍼시스턴스 잔차 구조를 쓰는 이유와 동일한 문제인데, 분류 헤드에서도 같은 원인이 작동한다는 것을 오랫동안 인지하지 못했다. **F1 0.813은 이 결함을 탐지할 수 없었다** — 폭염 라벨은 공식 특보 기록이 있는 표본에서만 채점하므로 겨울 표본은 애초에 채점 대상이 아니었다. 극한기상 헤드에 부호가 살아 있는 표현(`v_Z`)을 함께 넣어 해결했다(85.7% → 0.08%). 상세 내용은 [계절 오탐](#seasonal-false-alarm)을 참조한다. 교훈: 라벨 마스크가 특정 구간을 제외하면 그 구간은 지표가 영원히 보지 못한다 — 마스크로 가려진 영역은 라벨과 무관한 방법으로 따로 점검해야 한다.
- (2026-08-17) 위 수정을 배포한 직후 화면 전체가 `TypeError`로 멈췄다. <details id="6-논문의-위상각은-이-구현에서-수학적으로-퇴화한다">
<summary><b>6. 원 논문의 위상각(phase angle)은 본 구현에서 수학적으로 퇴화한다</b></summary>

Phase 3-6에서 원 논문의 위상 필터(θ<30°/30–80°/>80°)를 경보 게이트 상태로 사용하고자 θ를 실제로 계산한 결과, 본 구조에서는 정보량이 없는 값이었다.

```
θ = atan2(‖w_im·v_im‖, ‖w_re·v_re‖)
  세 인코더가 모두 F.normalize 출력 → ‖v‖ = 1
  ∴ θ = atan2(w_im, w_re)          ← 게이트 배분의 재표현일 뿐
```

`test_phase36.py` T1에서 두 값의 최대 차이가 1.19e-07로 확인되었다. θ가 축 자체의 표본별 정보를 담지 못하고, 게이트 가중치를 극좌표로 재표현한 값에 불과하다는 의미다. 검색 과제(원 논문)에서는 축 임베딩의 노름(norm)이 자유로워 θ가 의미를 가지나, 단위 정규화를 사용하는 본 회귀 구현에서는 해당 개념이 성립하지 않는다. 표본별 축 정보는 축 간 코사인(`cos(Re,Im)` 등, 표준편차 0.109 — `distribution_diagnostics.py`로 측정)에만 남아 있어, 상태에는 이를 대신 포함했다.

</details>

<details id="7-ppo는-본-규모에서-지도학습-기준선을-능가하지-못했다">
<summary><b>7. PPO는 본 규모에서 지도학습 기준선을 능가하지 못했다</b></summary>

경보 문제는 강화학습(RL) 적용 근거를 갖추도록 설계했다 — 비대칭 비용(미탐지 −20 : 오경보 −1), 이산 행동, 경보 피로(최근 경보가 누적되면 다음 오경보 비용이 증가)다. 피로 항으로 인해 보상이 과거 행동에 의존하므로 이 문제는 밴딧(bandit)이 아니라 진정한 MDP이며, `test_phase36.py` T5가 이를 수치로 확인한다(동일 관측·동일 행동이라도 이력에 따라 보상이 −1.00과 −2.00으로 상이하다).

그럼에도 4-fold 교차검증에서 PPO는 열세를 보였다(−0.173 vs 지도학습 −0.112, 고정 임계값 −0.139). 조건은 대칭으로 통제했다 — 모든 방법이 동일한 7개 관측소로 적합(fit)하고, 동일한 2개 관측소에서 임계값·반복 횟수를 선정하며, 나머지 3개에서만 평가했다.

열세의 원인은 두 가지로 판단한다.

1. **MDP 구조는 존재하나 규모가 작다.** 최적 경보율이 5~9% 수준이며, 이 구간의 정상상태 피로는 약 0.5로 오경보 비용 배수가 1.5배에 불과하다. 순차적 결합이 존재하나 지배적이지 않아, PPO가 확보할 수 있는 이득 자체가 제한적이다.
2. **표본이 부족하다.** 이벤트가 전체 214개(fold당 약 130개)에 불과하다. 지도학습은 표본마다 정답 라벨을 직접 수신하나, PPO는 동일한 신호를 표집된 리턴(return)에서 스스로 추출해야 한다. 이 격차가 위 1항의 제한적 이득을 상쇄한다.

부수적으로 다음을 확인했다. 상태에 게이트 가중치·θ·기압·습도를 포함한 조건(full)은 적합 보상이 −0.132로 최선이었으나 검증은 −0.200으로 최악이었다(격차 0.069). 게이트 입력에 위도·경도가 포함되어 있어(`train.record_to_vec` 인덱스 10·11) 이 특성들이 실질적으로 관측소 식별자로 작동했기 때문이다. 지점 불변 물리량만 남기자 격차가 0.014로 축소되었다 — 관측망 공백 지대까지 예측하는 것을 목표로 하는 시스템에서 정책이 지점을 암기하고 있었다는 의미이며, 본 프로젝트의 핵심 문제의식에 직결되는 결함이었다.

</details>

<details id="8-시간-분할-검증은-본-데이터에서-불가능했다">
<summary><b>8. 시간 분할 검증은 본 데이터에서 불가능했다</b></summary>

초기에는 관측소별로 앞 70%를 학습, 뒤 30%를 검증으로 설정하고자 했다. 그러나 수집 구간(2026-07-08~08-07)이 장마 종료 경계를 가로지른다.

| 구간 | 평균 강수 | 돌발 강수 이벤트 |
|---|---|---|
| 앞 70%(7/8~7/29, 장마) | 0.695mm | 212개 / 5,973(3.55%) |
| 뒤 30%(7/29~8/7, 폭염) | **0.000mm** | **2개 / 2,573(0.08%)** |

검증 구간에 강수가 전무하여 평가 자체가 성립하지 않았다. 관측소를 3개씩 4묶음으로 나눈 교차검증으로 전환하여, 모든 fold가 동일 기간을 공유하고 8,546쌍 전량이 정확히 1회씩 검증셋이 되도록 했다. 30일 수집으로는 계절 일반화를 측정할 수 없다는 의미이며, 데이터 기간을 1년 이상으로 확장해야 해결 가능한 문제였다.

> **후속(2026-08-16)**: 데이터가 13년으로 확장되면서 시간 분할 검증이 처음으로
> 가능해졌다. 실측 결과는 아래 9번 항목을 참조한다.

</details>

<details open id="9-검증-분할이-일-단위-라벨을-누수시키고-있었다">
<summary><b>9. 검증 분할이 일 단위 라벨을 누수시키고 있었다</b>(가장 최근이자 가장 중요한 발견)</summary>

13년치로 데이터를 확장하여 재학습한 결과 강수·극한기상 지표가 전반적으로 저하되었다(황사 F1 0.588→0.316). 표본이 4배 증가했음에도 성능이 저하된 것이 이례적이어서, 검증 설계 자체를 재검토했다.

**원인**: 폭염·한파·황사 라벨은 (관측소, 날짜) 단위로 부여된다. 특보가 발효된 날은 해당 일의 24개 시각 표본 전체가 동일한 라벨을 받는다. 그러나 학습·검증 분할은 시각 단위 무작위였다. `split_leakage_check.py`로 확인한 결과, 판정 가능한 검증 표본의 100.00%가(양성 표본만 산정해도 100.00%) 학습셋과 동일 날짜 짝을 보유했다. 일일 평균 표본이 23.9개이므로, 하루 전체가 한쪽에만 배정될 확률은 0.8²⁴≈0.5%에 불과해 실질적으로 필연적인 결과였다. 모델은 학습 과정에서 해당 관측소·날짜의 정답을 이미 확인한 상태로 검증받고 있었다 — 일반화 성능이 아니라 "동일 날짜의 다른 시각 예측"을 평가해온 것이다.

날짜 단위로 12개 관측소 전체를 한쪽에 배정하는 그룹 분할로 전환하자(관측소가 아닌 날짜 단위로 묶은 이유: Re축이 동일 시각 다른 11개 관측소의 실측값을 입력으로 사용하므로, 관측소별 분할 시 입력을 경유한 누수가 잔존한다) 극한기상 F1이 대폭 하락했다.

| 지표 | 무작위 분할(누수 존재) | 날짜 그룹 분할(누수 없음) |
|---|---|---|
| 폭염 F1 | 0.833 | 0.813 |
| 한파 F1 | 0.658 | 0.384 |
| 황사 F1 | 0.320 | 0.150 |

희소 사건일수록 낙폭이 컸다(한파 −0.274, 황사 −0.170) — 표본이 적은 사건일수록 "동일 날짜를 이미 학습했다"는 지름길에 더 크게 의존하고 있었다는 의미다. 폭염(양성률 24%, 기온이라는 강한 물리 신호)은 영향이 미미했다.

"데이터 확장 자체가 손실이었는가"를 검증하기 위해, 배포 중이던 이전 체크포인트(3.6년 학습)와 신규 체크포인트를 둘 다 학습에 사용하지 않은 동일 표본(2013~2022년 중 그룹 분할 검증셋)에서 직접 비교했다.

| 지표 | 이전 체크포인트(3.6년) | 신규(13년, 그룹 분할) |
|---|---|---|
| 강수 MAE(기준선 대비) | −26.6% | **−18.7%** |
| 폭염 F1 | 0.691 | **0.773** |
| 한파 F1 | **0.392** | 0.374 |
| 황사 F1 | 0.078 | **0.167** |

동일 기준으로 재평가한 결과 신규 모델이 대체로 우세했다 — 이전 체크포인트의 높은 F1은 대부분 검증 누수가 만든 착시였다. 원상복구하지 않고 신규 체크포인트를 그대로 배포했다.

본 사건을 계기로 다음 두 가지를 확정했다. ① 본 프로젝트의 모든 극한기상 F1은 이후 날짜 단위 그룹 분할로 측정한다. ② 사건 단위(일 단위·에피소드 단위)로 정의되는 라벨은 해당 단위로 분할하지 않으면 검증이 성립하지 않는다는 것을 원칙으로 기록한다.

**후속 — 시간 분할 교차검증(2026-08-16).** 그룹 분할과 별개로, 데이터가 13년으로 확장되면서 처음 가능해진 시간 분할(과거로 학습, 미래로 검증)도 컷오프(cutoff) 세 지점으로 검증했다. 배치 1024, 학습률 1e-3, 마스킹 ON은 모든 조건에서 동일하다. 아래 표는 12차원 구성에서 측정한 값이며, 현행 모델(14차원 + 부호 표현)로 재측정하지 않았다 — 분할 방식 간 상대 비교를 위한 기록이다.

| 분할 | 검증 구간 | 기온 MAE | 강수(기준선 대비) | 폭염 F1 | 한파 F1 | 황사 F1 |
|---|---|---|---|---|---|---|
| 그룹(날짜 단위) | 2013~2026 전체 중 20% | 1.3551°C | −17.9% | 0.813 | 0.384 | 0.150 |
| 시간, 2021 컷오프 | 2022~2026 | 1.3527°C | −16.6% | 0.774 | 0.408 | 0.106 |
| 시간, 2023 컷오프 | 2024~2026 | 1.3172°C | −18.6% | 0.763 | 0.433 | 0.108 |
| 시간, 2024 컷오프 | 2025~2026 | 1.3311°C | −13.1% | 0.746 | 0.433 | 0.112 |

컷오프를 2021→2023→2024로 지연시킬수록(검증 구간이 최근에 근접할수록) 폭염 F1은 지속적으로 하락하고(0.774→0.763→0.746) 한파 F1은 지속적으로 상승한다(0.408→0.433→0.433) — 시간 분할을 단일 지점만 검토했다면 이 경향을 노이즈로 오판했을 것이다. 연도별 실제 기후 및 라벨 구성 변화로 해석한다(폭염은 최근일수록 양성률이 상승하는 경향, 한파는 반대). 황사는 분할 방식과 무관하게 지속적으로 낮다(F1 0.11~0.15) — 표본 또는 분할의 문제가 아니라, 앞서 제외한 사유(구조적 판별 신호 부족)가 타당함을 뒷받침하는 추가 증거다.

개발·비교용 기본 기준은 계속 날짜 그룹 분할을 사용한다(분산이 작고 계절이 양쪽에 고르게 분포한다). 시간 분할은 "실제 운영 환경에서 기대할 성능"을 별도로 확인할 때 참고 지표로 사용한다.

</details>

## 재학습 필요성 — 자동화 검토

실시간 관측은 모델을 재학습시키지 않는다. 화면에 표시되는 모델은 고정된 체크포인트이며, 5분마다 갱신되는 관측값은 다음 두 용도로만 사용된다.

1. **추론 입력** — 현재 시점의 관측값(인접 11곳 + 과거 1·3·6시간 포함)을 입력하여 6시간 후를 산출한다. 가중치는 변경되지 않는다.
2. **적중률 기록** — 출력값을 로그에 기록하고 6시간 후 실측값이 확정되면 대조한다. 이 대조 결과 역시 모델을 변경하지 않는다 — 순수한 사후 모니터링이다.

온라인 학습(관측 1건마다 즉시 가중치를 갱신하는 방식)은 의도적으로 포함하지 않았다.

| 근거 | 내용 |
|---|---|
| 표본 밀도 | 관측소당 신규 표본이 시간당 1건이다. 배치 1 에폭이 처리하는 수만 건 규모의 그레디언트 평균과 달리, 1건 단위 업데이트는 노이즈가 학습 신호를 초과할 위험이 크다 |
| 재앙적 망각(catastrophic forgetting) | 최근 데이터에 즉시 맞춰 갱신하면 계절 패턴을 망각한다. 이를 방지할 리플레이 버퍼(replay buffer)나 정규화 장치가 아직 없다 |
| 재현성(reproducibility) | 배치 재학습은 "이 체크포인트 = 이 데이터 + 이 코드"를 그대로 감사·재현할 수 있다. 온라인 학습은 매 순간 가중치가 변화하여 동일 상황을 재현하기 어렵다 |

### 주기적 재학습의 필요성 — 필요하다

기후 데이터는 계절 순환이 지배적이므로, 학습셋에 없는 계절 구간은 모델이 미경험 상황을 추정해야 한다. 실제로 본 프로젝트도 초기 30일 수집(2026-07~08, 장마에서 폭염으로 전환되는 경계)에서 검증 구간에 강수가 전무하여 평가가 성립하지 않는 문제를 겪었으며([한계 8](#8-시간-분할-검증은-본-데이터에서-불가능했다)), 데이터를 3.5년으로 확장한 후에야 해결되었다. 따라서 재학습 주기는 분기~반기 단위가 합리적이다(월 단위는 신규 표본이 전체의 2% 내외로 이득이 제한적이다).

### 자동화 가능 범위 — 부분 자동화가 현실적이다

| 단계 | 자동화 여부 | 근거 |
|---|---|---|
| 신규 관측 수집 | ✅ **이미 자동화됨** | `.github/workflows/refresh-data.yml`(Cloudflare Cron Trigger가 15분마다 깨움, `data` 브랜치에 커밋) + `refresh_deploy_data.py` |
| 극한기상 라벨 갱신 | ⚠️ **반자동** | '날씨 이슈별 데이터'·PM10은 포털에서 수동 다운로드가 필요하다(API 미제공). `import_weather_issues.py`가 파싱은 자동 수행한다 |
| 재학습 실행 | ⚠️ **로컬 GPU 필요** | GitHub Actions 무료 러너는 GPU를 제공하지 않는다. 전체 학습에 약 25분(GPU 기준)이 소요된다 |
| 체크포인트 검증·승격 | ✅ **이미 자동화됨**(2026-08-17) | `promote_checkpoint.py <후보>` — 계절 오탐·단조성·관측소 라벨 사각지대·회귀 성능 4개 게이트를 통과해야 승격되고, 통과 후 확률 보정 재적합·산출물 재생성까지 자동으로 이어진다. 하나라도 FAIL이면 배포 경로를 건드리지 않는다. 실제로 겨울 폭염 오탐이 재발한 후보(계절 오탐 38.8%)를 차단한 실적이 있다 |

**권장 운영 방식**: 관측 수집만 상시 자동으로 실행하고(현재 구현됨), 분기마다 ① 포털에서 라벨 CSV를 수동 다운로드하고 ② 로컬 GPU에서 `train.py`를 실행하고 ③ `promote_checkpoint.py <후보>.pt --promote`로 게이트를 통과한 경우에만 승격한다. 재학습 전 반드시 백업하는 규칙(`numerical_trichef_vN_<사유>.pt`)은 유지되며, 신규 헤드 추가 시마다 강수 MAE를 재확인하는 규칙도 게이트 3(회귀 성능)에 포함되어 자동으로 검증된다. 승격 스크립트가 마지막에 출력하는 남은 수동 작업(임계값 상수·README 수치·스크린샷 갱신)만 사람이 처리한다.

## 환경 주의사항

본 저장소의 `requirements.txt`를 전역 Python 환경(가상환경 미사용)에 설치하면 `numpy<2`, `pillow<11` 등 Streamlit의 의존성 제약으로 인해 동일 환경의 다른 프로젝트가 손상될 수 있다. 가상환경 사용을 강력히 권장한다.

```bash
python -m venv .venv
.venv\Scripts\activate      # Windows
pip install -r requirements.txt
```
